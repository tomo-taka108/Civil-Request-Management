1テストは何のためにあるか

ひとことで：手でやっている確認をプログラムに任せ、「壊れたらすぐ気づける」状態を保つこと。

機能を作ったら、ブラウザで画面を開いて、ボタンを押して、表示を目で見て確かめます。テストコードは、この「目で見て確かめる」部分をプログラムに書き起こしたものです。

// 手でやっていること
ログインする → 一覧で「対応状況：対応中」を選ぶ → 対応中の案件だけ出るのを目で見る

// テストにすると（PHPUnit）
$this->actingAs($user)->get('/requests?response_status[]=in_progress')
     ->assertSee('対応中の案件')->assertDontSee('完了した案件');

テストの本当の価値

一度書けば、コマンド1つで何百回でも同じ確認を繰り返せます。価値は「今動く」ことの確認よりも、あとで別の場所を直したときに、うっかり壊したことにすぐ気づける点にあります。

たとえ：健康診断。受けた瞬間に健康になるわけではないけれど、去年と比べて悪くなった所が分かる。テストも「前と変わってしまった」ことを教えてくれる仕組みです。

テストが確かめたいことは、大きく3つに分けられます。

問い例主なテスト
正しく動くか検索条件どおりに絞り込まれるか、権限のない人は編集できないか単体・結合・E2E
速く・たくさん動くか30人が同時に使っても待たされないかパフォーマンス
使う人の目的を果たせるか受付から完了報告まで、業務の流れどおりに使えるか総合・受入（手動が中心）

2テストの種類の地図（2つの軸）

ひとことで：「単体・結合・総合」は範囲の大きさ、「パフォーマンス」は確かめる性質の名前。軸が違うので、同じ列に並べると混乱する。

「単体テスト、結合テスト、総合テスト、パフォーマンステスト、E2E テスト」と並べると、5種類の別々のテストがあるように見えます。実は違う物差しの名前が混ざっています。2つの軸で整理するとすっきりします。

軸1：どこまでの範囲をつないで確かめるか

単体テスト部品1つだけ。関数やクラス単位
→
結合テスト部品をつないで。画面の裏側（コントローラ＋DB）まで
→
E2E テスト本物のブラウザで、画面操作の最初から最後まで

右に行くほど本番に近いけれど、遅く・壊れやすく・失敗したときに原因を探しにくくなります。

軸2：何を確かめるか

機能テスト

仕様どおりの「結果」になるか

検索・登録・権限・バリデーションなど。上の単体〜E2E は、基本的にこちらを確かめます。

非機能テスト

結果は正しい前提で、「どう動くか」

パフォーマンス（速さ・同時に耐えられる人数）、セキュリティ、使いやすさなど。結果が合っていても、10秒かかったら使えません。

「総合テスト」はどこに入るのか（工程の名前）

日本の開発現場では、テストを作業の工程（フェーズ）で呼ぶことが多く、「単体 → 結合 → 総合 → 受入」と進みます。これは設計書と対になっていて、V字モデルと呼ばれます。

設計（左側）テスト（右側）確かめること
要件定義↔受入テスト利用者が「これで業務ができる」と認めるか
基本設計（画面・DB）↔総合テスト（システムテスト）システム全体として要件を満たすか。性能・セキュリティもここで見ることが多い
詳細設計↔結合テスト部品同士が正しくつながるか
実装↔単体テスト部品1つが正しく動くか
🔑呼び方の違いに注意。工程の「総合テスト」は、テスト仕様書を作って人が手で確認することも多い工程の名前です。一方「E2E テスト」は、ブラウザ操作をプログラムで自動化する技術の名前。総合テストの一部を E2E で自動化する、という関係になります。また、パフォーマンステストは総合テストの工程で行うことが多い「非機能テスト」の代表です。

3テストピラミッド

ひとことで：速くて安いテストを下にたくさん、遅くて高いテストを上に少しだけ。

手動確認・探索的テスト
人が触って違和感を探す。数は最小限
E2E テスト
本物のブラウザで主要な流れだけ
結合テスト
HTTP → コントローラ → DB まで通す
単体テスト
関数・クラス単位。一瞬で終わる
静的解析・コード整形
動かさずにコードを読んで型の間違い等を見つける（厳密にはテストの手前の土台）
↓ 下ほど：速い・安い・原因が分かりやすい上ほど：本番に近い・遅い・壊れやすい ↑

この形になる理由は、失敗したときのコストです。単体テストが落ちれば「この関数のこの行」とすぐ分かりますが、E2E テストが落ちると「画面のどこか・サーバーのどこか・DB のどこか」から探すことになります。さらに E2E は1本に数十秒かかり、ボタンの文言を変えただけで落ちることもあります。

⚠️逆三角形（アイスクリームコーン）は避ける。手動確認と E2E ばかりで、下の層が薄い状態のこと。テストに時間がかかるので回す回数が減り、結局「壊れても気づかない」に戻ってしまいます。

Laravel では「結合テスト」が厚くなりやすい

ピラミッドは目安で、形はアプリの性質で変わります。Laravel の画面アプリは、処理の多くが「リクエストを受けて、DB を検索して、画面を返す」ことでできています。この場合、DB を偽物にした単体テストでは自分で書いた検索条件（SQL）が1行も実行されず、肝心なところを確かめられません。

そのため Laravel では、本物の DB につないで HTTP リクエストから通す Feature テスト（＝結合テスト）が中心になるのが普通です。Laravel の Feature テストは DB を毎回まっさらに戻すので、結合テストでも1本あたり平均0.5秒ほどで回ります（このアプリは204本で約97秒）。

静的解析・コード整形 実施中

道具：Pint（整形）、PHPStan / Larastan（静的解析）

プログラムを動かさずに読んで、存在しないメソッドの呼び出しや型の食い違いを見つけます。テストを書かなくても効くので、ピラミッドの土台に置かれます。

たとえ：提出前の誤字脱字チェック。内容が正しいかまでは分からないが、明らかなミスは一瞬で見つかる。
このプロジェクトでは
  • pint.json：整形のルール（Laravel の標準ルール。テスト名に日本語を使えるよう1つだけ外している）
  • phpstan.neon：解析の設定。対象は app/・database/・routes/、厳しさはレベル5（0〜10）
  • テスト用のファイルを別に書く必要はない。設定ファイルだけで、書いたコード全体を自動で調べる

単体テスト（Unit） ほぼ無し

道具：PHPUnit（tests/Unit）

1つの関数・クラスを、周りから切り離して確かめます。DB もファイルも使わないので一瞬で終わります。向いているのは計算・変換・判定などの「ロジックだけ」の部品です。

例：「対応状況の値 in_progress を画面用の文字『対応中』に変える」関数。

このプロジェクトでは
  • tests/Unit/ExampleTest.php の1本だけ。Laravel がプロジェクト作成時に入れる見本（「true は true」を確かめるだけ）
  • 上の例の関数は app/Support/RequestLabels.php にあるが、単体テストは無い（画面の Feature テストで「対応中」と表示されることを間接的に確かめている）

結合テスト（Laravel では Feature テスト） 203本

道具：PHPUnit（tests/Feature）＋テスト専用 DB

ブラウザの代わりに HTTP リクエストを送り、ルーティング → ミドルウェア（ログイン確認）→ バリデーション → コントローラ → DB → 画面（HTML）まで通しで確かめます。ただしJavaScript は動きません（返ってきた HTML の文字を調べるだけ）。

例：一般職員でログインして一覧を開くと、自分の事務所の案件だけが表示される。

このプロジェクトでは
  • tests/Feature/*.php：テスト本体（17ファイル。内訳は8章）
  • tests/TestCase.php：全テスト共通の土台
  • database/factories/*.php：テスト用データの作り方（事務所・ユーザー・案件・対応履歴・写真の5つ）
  • phpunit.xml：テスト時の設定。テスト専用 DB を使う、ログを書かない、など
  • docker/mysql/init.sql：テスト専用 DB（civil_request_management_testing）を最初に作る

E2E テスト（End to End） 実施済み（2026-10-25）

道具：Playwright（Chromium）

本物のブラウザ（Chrome 等）をプログラムで操作して、利用者と同じように画面を触ります。JavaScript も CSS も実際に動くので、Feature テストでは確かめられない「地図にピンが立つ」「ボタンを押したら入力欄が切り替わる」なども見られます。

例：ログイン → 詳細画面で写真つきの対応履歴を追加 → 写真が実際に表示される。

このプロジェクトでは
  • e2e/specs/*.spec.ts：テスト本体（6ファイル・7本＋任意の1本。一覧は docs/e2e-test.md 4章）
  • e2e/fixtures/test.ts：全テスト共通の準備（地図タイルのダミー差し替え、画面の JavaScript エラーの見張り、ログイン）
  • e2e/fixtures/data.ts：試験データのユーザー ID・案件の文面（Seeder と対応）
  • e2e/playwright.config.ts：設定（1つずつ順に流す、失敗時に画面の写真と操作の記録を残す、など）
  • e2e/run-e2e.sh：環境の起動 → データ投入 → テスト → 片付けを1本で行うスクリプト。手順は e2e/README.md
  • docker-compose.e2e.yml：試験専用の環境（本番と同じイメージ＋試験専用の MySQL。ポート 8083）
  • database/seeders/E2eDataSeeder.php：ユーザー4人・案件7件の決め打ちのデータ。試験専用 DB 以外では動かない（tests/Feature/E2eDataSeederTest.php で確認）
  • docs/e2e-test.md：設計と結果

Playwright とは・ほかのツールとの比較

Playwright は Microsoft が作っている、ブラウザを自動で操作するツールです。「このボタンを押す」「この文字が出ているはず」を TypeScript（または JavaScript）で書くと、本物のブラウザで順に実行して、合否を出します。

ツール特徴このアプリに対して
Playwright（採用）待ち合わせを自動でしてくれる。ブラウザの通信を途中で差し替えられる。失敗時の記録（トレース）が見やすい◎ 地図タイルをダミーに差し替えられる。SnsTimeLineApp でも使っている
Cypress画面を見ながらテストを作りやすい○ 通信の差し替えもでき十分使えるが、1つのテストで複数のタブを扱えない。SnsTimeLineApp で選ばなかった道具でもある
Selenium最も歴史が長く、対応言語が多い△ 「表示されるまで待つ」を自分で書く必要があり、不安定になりやすい
Laravel DuskLaravel 公式。PHP で書ける○ PHP で書けるのは魅力。ただし中身は Selenium 系の仕組みで、通信の差し替えなどは Playwright のほうが得意

動かすのに必要なもの（k6 との違い）

k6 はパソコンに1つ入れれば、どのプロジェクトからも同じものを使えます。Playwright はプロジェクトごとに版を決めて入れるのが基本で、さらにその版に合ったテスト用のブラウザも別に入れる必要があります。

もの入れる場所このプロジェクトでは
Node.js（土台）パソコン本体もともと入っていたもの（v24）を使用
Playwright 本体プロジェクトごと（e2e/node_modules/）cd e2e && npm ci で入れる。版は 1.64.0 に固定（e2e/package.json）。Git には入れない
テスト用のブラウザ（Chromium、約120MB）パソコンの共通の置き場（C:\Users\<ユーザー名>\AppData\Local\ms-playwright\）。版ごとにフォルダが分かれるnpx playwright install chromium で入れる。同じ版の Playwright を使うプロジェクト同士なら共有される

どちらもインターネット経由（npm の公式の配布元と、Playwright の公式の配布元）でダウンロードします。最初に一度だけ実行すればよく、手順は e2e/README.md にあります。パソコンにはほかのプロジェクト用の Playwright（版違い）も入っていましたが、版が合わないため使っていません。実際に入れた版と、改ざんを確かめるための値は e2e/package-lock.json に記録されており、別の PC でも npm ci で同じものが入ります。

🗺️地図タイルはダミーに差し替える。地図の背景画像（国土地理院のタイル）は、テスト中は灰色の無地の画像を返します。外のサーバーの調子や回線で落ちないようにするためと、相手のサーバーに負担をかけないためです。差し替えるのは背景だけで、ピンの表示やクリックなどこのアプリの JavaScript は本物のまま動きます。本物を読み込む確認は、任意で流す1本（E2E_REAL_TILES=1）とデプロイ後の目視で補います。

5パフォーマンステストを詳しく

ひとことで：「何人で・どれくらいの時間・どの操作を」したときに「どれくらいの速さで返るか」を測る。

種類（かける負荷の形で呼び名が変わる）

名前かける負荷分かること
負荷テスト（ロードテスト）想定どおりの人数（このアプリなら30人）を一定時間普段の使われ方で十分速いか。まずはこれ
ストレステスト想定を超えて人数を増やし続ける何人で限界が来るか、限界のときどう壊れるか
スパイクテスト急に人数を跳ね上げる朝礼直後に全員が開くような瞬間に耐えるか
耐久テスト（ソーク）普段の負荷を数時間続けるメモリがじわじわ増える等、時間がたって出る問題

見る数字

指標意味読み方のコツ
応答時間 p95全リクエストを速い順に並べて、95%目の時間平均ではなく p95 を見る。平均は速いリクエストに引っぱられ、遅い一部の人の体験が隠れる
エラー率失敗したリクエストの割合速くてもエラーで返していたら意味がない。0% が基本
スループット1秒あたりに処理できたリクエスト数人数を増やしても伸びなくなった所が限界の目安
サーバーの様子CPU・メモリ（docker stats）遅くなったとき「どこが詰まっているか」を探す手がかり

k6 とは

k6（ケーシックス）は、Grafana Labs が作っている負荷試験のツールです。「どの画面を、どんな順番で、何人で開くか」を JavaScript で書いたシナリオとして用意すると、k6 がその人数分の仮想ユーザー（VU）を作り、同時に動かして応答時間を集計します。

// このアプリのシナリオ（perf/scenarios/daily.js）のイメージ
login('perf01');                      // 最初に1回ログイン
page('/dashboard');  sleep(3);         // ダッシュボードを開いて、3秒くらい眺める
page('/requests');   sleep(3);         // 一覧
page('/requests?keyword=草');       // 検索 → 詳細 …を30人分同時に繰り返す

結果は「画面ごとの p95 が1秒未満か」のような合格ラインを決めておくと、自動で合否を出してくれます（不合格なら終了コードが0以外になる）。

ほかのツールとの比較（なぜ k6 か）

ツールシナリオの書き方動かすのに要るものこのアプリに対して
k6（採用）JavaScript のコードk6 本体（1つの実行ファイル）だけ◎ 読みやすく差分も追える。追加の言語環境が要らない
JMeter画面（GUI）で組み立て、巨大な XML で保存Java△ 老舗で情報は多いが、保存ファイルを読んで直すのがつらい
GatlingJava・Scala などのコードJava（JVM）△ 高機能だが、PHP のプロジェクトに Java を持ち込むことになる
LocustPython のコードPython○ 書きやすいが、このプロジェクトに Python の環境が無い
ab・wrkコマンド1行（1つの URL を連打）本体のみ✕ 「ログイン → 一覧 → 詳細」のような流れを表せない

決め手は次の4つです。

  • 流れを書ける：ログイン（CSRF トークン・セッション Cookie）→ 検索 → 詳細 → 対応履歴の書き込み、という業務の流れをそのまま表せる
  • コードなので Git で管理できる：シナリオの変更が差分で見え、レビューもしやすい
  • 軽い：k6 本体だけで動き、Java・Python などを新しく入れずに済む
  • 合否を自動で出せる：合格ライン（thresholds）を書いておけば、毎回同じ基準で判定できる。SnsTimeLineApp でも使っていて、PC にもすでに入っている

SnsTimeLineApp ではシナリオを TypeScript で書きましたが、このアプリは TypeScript を使っていないため、素の JavaScript で書いています。

⚠️ローカルで測った数字を「本番の実力」と言わない。パソコン1台の中で、負荷をかける側（k6）とアプリと DB が CPU を取り合うためです。ローカルの数字は「前回と比べて遅くなっていないか」「どこが詰まるか」を見るのに使います（SnsTimeLineApp と同じ考え方）。
🚫本番には負荷をかけない。本番の EC2 は famigo と共用の小さなサーバー（t3.micro）です。負荷をかけると famigo まで止まりかねず、アラームも鳴ります。

6ブラックボックスとホワイトボックス

ひとことで：テストの「ケース（何を試すか）」を、仕様書を見て決めるか、コードの中身を見て決めるか、という視点の違い。

2章の「単体・結合・E2E」はどこまでつなぐかの話でした。ここでの話はそれとは別で、どの値を試して、どうなれば正解とするかを、何を見て決めるかです。どの種類のテストにも両方の視点が使えます。

⬛ ブラックボックス 正解はこちらで決める

仕様書だけを見る。中身のコードは見ない

  • 「要望内容は2,000文字まで」と書いてあれば、2,000文字と2,001文字を試す
  • コードがどう書かれているかは関係ない
  • コードの勘違いに引きずられないのが最大の利点
たとえ：自動販売機をお金と出てくる商品だけで確かめる。中の仕組みは知らなくていい。

⬜ ホワイトボックス 漏れ探しに使う

コードの中身（if 文の分かれ道など）を見る

  • if が3つあれば、3つの道をすべて通るケースを用意する
  • 失敗したときの後片付けなど、仕様書には書かれない道を拾える
  • ただし、コードの勘違いをそのまま正解にしてしまう危険がある
たとえ：自動販売機のふたを開けて、つり銭切れのときの動きまで確かめる。
⚠️ホワイトボックスだけだと危ない理由。仕様が「上限2,000文字」なのに、コードが間違って「上限1,000文字」になっていたとします。コードを見てテストを書くと「1,001文字でエラーになること」を正解として書いてしまい、テストは緑のまま。バグをテストで固めてしまうことになります。だから正解（期待値）は仕様書から決め、ホワイトボックスは「試し忘れている道がないか」の確認に使います。

ケースを決める3つの技法（主にブラックボックス）

技法考え方このアプリでの例
同値分割入力を「同じ結果になるグループ」に分け、各グループから1つずつ試す対応状況（未着手・対応中・完了…）ごとに1件ずつ作って検索する
境界値分析グループの境目（上限ちょうど・1つ超え）を狙う。バグは境目に出やすい要望内容がちょうど2,000文字なら登録できる／2,001文字ならエラー
組み合わせ（デシジョンテーブル）条件が複数あるとき、組み合わせを表にして漏れを防ぐ役割（管理者・一般職員）×事務所（自分・他）×部署（担当・担当外）で、編集できるかどうか

このプロジェクトではどうしているか

視点実際のやり方・テストの例
確かめ方はブラックボックスFeature テストは、HTTP リクエストを送って「返ってきた画面」「DB に残ったデータ」だけを見ています。コントローラの中でどう処理したかには触れません。そのため、中身を書き直しても、利用者から見た動きが同じならテストは通り続けます
正解は設計書からCLAUDE.md 7.2 のとおり、実装前に要件定義書・画面設計書・DB 設計書と突き合わせています。例：RequestControllerTest の「ちょうど2,000文字なら登録できる」「2,000文字を超えるとエラー」（上限は画面設計書と Issue #49 で決めた値）、RequestIndexTest の「一般職員は自事務所の案件のみ表示される」（要件定義の事務所スコープ）

ホワイトボックスで足した例コードの中身を知っているから書けたテストもあります。
・RequestPhotoTest「拡張子を png に偽装した SVG は登録できない」：ファイル名ではなく中身で形式を判定している、という実装を知っていて狙ったもの
・LoggingTest「写真の保存に失敗したら ERROR で記録し例外は投げ直す」：保存先をわざと壊して、失敗したときの道を通している
・LoggingTest「DB エラーのログには SQL に埋め込まれた値を出さない」：エラー時の処理（bootstrap/app.php）を知っていて狙ったもの
🔑まだ無いもの：テストケース表。SnsTimeLineApp では、テストを書く前に「入力・期待値・根拠（設計書のどこか）」の表（docs/11_test_design.md）を作りました。このプロジェクトでは表は作らず、設計書を見ながら直接テストを書いています。規模が小さいうちはこれで回っていますが、条件の組み合わせが多い権限まわりなどは、表にすると漏れが見つかりやすくなります。

7テストを支える考え方

種類の話とは別に、どのテストにも共通する大事な点。

テスト用のデータは本番・開発と分ける

テストはデータを作っては消すので、普段使う DB でやると中身が壊れます。このアプリは テスト専用 DB（civil_request_management_testing）を使い、1本ごとにまっさらに戻しています。パフォーマンステストでも、大量データを入れる専用の DB を分ける予定です。

外の世界は「偽物」に置き換える

写真の保存先は、本番だけ S3 で、ローカル開発とテストでは PC 内のフォルダ（PHOTO_DISK=local）です。テストは最初から S3 には行きません。そのうえで、テストの目的に合わせて2通りの「置き場」を使い分けています。

やり方保存される場所使っているテスト
Storage::fake()（Laravel が用意した偽物）storage/framework/testing/disks/local/。呼ぶたびに中身が空になるLoggingTest、サンプルデータ関係のテスト
本物のローカルディスクを、テスト専用フォルダに向けるstorage/framework/testing/request-photos/。テストの前後で消すRequestPhotoTest

写真のテストで偽物を使わないのは、Storage::fake() が署名付きURLを、署名なしのURLに差し替えてしまうためです。「期限付きの署名付きURLでのみ表示する」という要件を確かめたいので、本物のディスクを使っています。偽物にすると、その部分は確かめていないことになる、という良い例です。

S3 そのもの（本番の保存・表示）は、テストでは確かめていません。本番での手動確認で補っています。

テストが本当に効いているか、わざと壊して確かめる

テストが緑でも、何も確かめていないテストかもしれません。守りたいコードをわざと消してテストが赤くなるかを見ると、テストが本物か分かります（ミューテーションテストの考え方）。ログ整備のときに、機密がログに出ないことを確かめるテストで実際にやりました。

🔑テストが全部緑でも、バグがゼロとは限らない。テストは「書いたことが正しい」としか教えてくれません。本数やカバレッジ（テストが通った行の割合）を増やすこと自体を目標にせず、「壊れたら困る所が守られているか」で考えます。

9今後の方針

ひとことで：パフォーマンス → E2E → CI の順に、それぞれ「小さく・必要な分だけ」足す。

① パフォーマンスk6・ローカルのみ
→
② E2EPlaywright・主要な流れ数本
→
③ CIGitHub Actions で PR ごとに自動実行

この順にするのは、要件の数字（30人）をまだ一度も確かめていないのがいちばん大きな穴だからです。E2E と CI は「今あるテストをより確実に回す・範囲を少し広げる」改善で、急ぎ度は一段下がります。

① パフォーマンステスト（k6）

項目方針
目的想定の30人が同時に使っても待たされないか確かめ、遅い画面があれば原因をつかむ
どこでローカルの Docker 環境だけ。本番には負荷をかけない
データテストを始める前に、専用の DB へ保存期間3年分（年間1,000件 × 3年 ＝ 約3,000件）の案件と対応履歴を入れておく。検索やダッシュボードの速さは「DB にどれだけ溜まっているか」で変わるため、3年運用した後の状態を先に作っておく（棚に3年分の書類がすでにある状態）。毎回同じ内容で入れる（同じデータでないと前回と比べられない）。実在の名前は使わない
シナリオ30人が、普段の使い方に近い操作をする。ほとんどは「見る」操作（ログイン → ダッシュボード → 一覧で検索 → 詳細）で、対応履歴の追加など「書く」操作は少しだけ混ぜる。操作の合間には数秒の間（考えている時間）を入れる。1人が大量に入力するような、業務で起きない操作はしない。地図・CSV 出力は別に測る
合格の目安p95 が1秒未満・エラー率0%（SnsTimeLineApp と同じ目安）。ただし数字は「前回比」と「詰まる場所探し」に使い、本番の実力とは言わない
CI に入れるか入れない。CI のサーバーは他の処理と CPU を分け合うので、数字が毎回ぶれて比べられない

コードを読んで、先に「詰まりそうな所」の仮説を立てておきます。測ってみて当たっているかを確かめるのがパフォーマンステストの醍醐味です。

仮説（試験前）理由結果（2026-10-24）
PHP の同時処理数php-fpm は既定のまま（同時に処理できるのは5件まで）。30人が同時に押すと順番待ちになる可能性外れ。1画面が数十ms で終わるので、60人でも5つの枠で回った
地図画面条件に合う案件を件数の上限なしで全部取り出している速さは問題なし、量に課題。管理者だとピンのデータが 1.77MB（圧縮なし）。回線が遅いと数秒かかりうる → 今後検討
ダッシュボード開くたびに全案件を数え直す集計が複数あるふだんは問題なし。ただし下の「思わぬ発見」あり
キーワード検索部分一致（LIKE '%…%'）は索引が効かず全件を見る問題なし。3,000件なら全件見ても約25ms

結果のまとめ

試験結果
30人（想定どおり）全画面の p95 が 60ms 以下（目安は1秒）。失敗0件
60人（想定の2倍）全画面が目安内（最大でも地図のピンのデータで p95 約0.2秒）。失敗0件
CSV 出力管理者・全件（約3,000件）で約0.5秒
🔑思わぬ発見：データを一気に入れた直後は、MySQL が遅い調べ方を選ぶ。最初の計測で、ダッシュボードだけまれに約0.9秒かかりました。調べると、「30日以上動きなし」を数える SQL が、データを一括で入れた直後だけ索引を使わずに全件を見ていました（0.58秒）。MySQL は表ごとの統計情報（どんなデータがどれくらいあるか）を見て調べ方を決めますが、一気に入れた直後は統計が古いままだからです。ANALYZE TABLE で統計を作り直すと 0.006秒（約90倍）になりました。ふだんの運用ではデータが少しずつ増え、統計も自動で追いつくので起きにくい現象です。将来、大量のデータを一括で取り込むときは、取り込んだ後に ANALYZE TABLE を実行すると安心です。
⚠️測り方の落とし穴。手で curl を使って測ったとき、localhost と書くと毎回約0.6秒余計にかかり、アプリが遅いと勘違いしかけました。Windows ではまず IPv6 で接続を試すためで、127.0.0.1 と書くと正しく測れます。「遅い」と感じたら、まず測り方が正しいかを疑うのも大事です。

② E2E テスト（Playwright）

項目方針・結果（2026-10-25）
本数7本に絞った。Feature テストで確かめられることはやり直さず、JavaScript が絡む所と業務の主な流れだけ
中身案件の登録（地図で位置を選ぶ）→ 一覧 → 詳細／編集・削除の確認ダイアログ／写真つきの対応履歴／地図のピンと絞り込み／管理者がユーザー登録 → 初回ログインでパスワード変更／他部署は閲覧のみ
環境・データパフォーマンステストと同じく、本番と同じイメージの試験専用の環境。データは「ピンは2本」と言い切れるよう、少ない件数を決め打ちで入れる
不安定さ同じ環境で3回ずつ繰り返して21本すべて成功。失敗しても再実行しない設定にして、不安定さを隠さない
効いているか地図のクリック・入力欄の切り替え・ピンの取り寄せをわざと壊すと、狙ったテストが落ちることを確認（7章のミューテーションの考え方）
🔑E2E で見つかった不具合：パスワード変更後のメッセージが出ていなかった。変更後に「パスワードを変更しました。」と出るはずが、実際の画面には一度も出ていませんでした。トップ（/）を経由してダッシュボードへ転送していたため、1回だけ表示されるメッセージが中継で使い切られていたのです。Feature テストは「トップへ転送される」ことまでしか見ていなかったので気づけませんでした。転送の先まで、利用者と同じ画面を見る E2E ならではの発見です。直したうえで、Feature テストにも「転送をたどった先にメッセージが出る」確認を足しました。

③ CI（GitHub Actions）

  • PR を出したら自動で Pint → PHPStan → PHPUnit を実行し、赤ならマージ前に分かるようにする（今ローカルでやっている quality-check と同じ中身）。2026-10-28 に導入（#128。.github/workflows/ci.yml、仕組みは ci-basics.html）
  • E2E は CI に入れていない：時間がかかり、落ちたときの原因調査も重いため。手元で回す運用にして、必要を感じたら手動で動かせる別のワークフローとして足す
  • パフォーマンステストは入れない（上記のとおり数字がぶれるため）

単体テストは「必要な所だけ」

このアプリは、DB とつながって初めて意味のある処理が大半です。単体テストの本数を増やすこと自体は目標にせず、ロジックだけの部品が増えたときに書きます。今の候補は、値を画面用の文字に変える RequestLabels や、編集・削除の権限を判定する RequestPolicy 程度です（どちらも Feature テストで間接的には確かめ済み）。

💡まとめ。今は「結合テストが厚く、その上下が薄い」形。Laravel としては自然な形なので崩さず、上に E2E を少し、横にパフォーマンスを1本足し、CI で回し忘れを防ぐ。どれも「本数を増やす」ではなく「今まで確かめられていなかった所を埋める」ために足す。
