Civil Track を AWS に公開するまで

「言われるがまま」進めた一連の作業が、結局“何のための何だったのか”。3つの幕に分けて、目的とやったことをたどります。

🎯 全体を一言で：AWSという土地に、Civil Track が動く「部屋」を用意し（第1幕）、本番用の設定をしたアプリを運び込んで（第2幕）、実際に動かして公開した（第3幕）。

第1幕インフラ構築（Terraform）

＝ アプリを置く「部屋」と「通り道」を AWS に用意する

🎯目的：ブラウザ →(HTTPS)→ ALB → EC2 → RDS という経路を通せるように、足りない部品を AWS に作る。既存の famigo 環境を壊さないよう「間借り（相乗り）」で。
1

Terraform のコードを書いた

AWS に「こういう部品を作って」と指示する設計図を infra/ に用意。手作業でポチポチ作る代わりに、コードで正確・再現可能に作る道具が Terraform。

なぜ：手作業だと間違えるし記録も残らない。コード化で「何を作ったか」が明確になり、famigo に触れないことも保証しやすい。
2

独自ドメイン civil-track.com を取得

お名前.com で購入し、その「住所案内（DNS）」を AWS の Route53 に向けた（ネームサーバー4つを登録）。

なぜ：利用者がアクセスする入口の名前。famigo の名前を間借りせず、独立した名前にするため。
3

Terraform を実行して AWS に部品を作った

plan（作らずに差分を確認）→ apply（実際に作成）。作ったのは：HTTPS証明書(ACM)・DNS(Route53)・振り分け先(ターゲットグループ)・振り分けルール(ALBに1本追加)・通信許可(SGに8081を1行追加)。

なぜ：「ブラウザ→ALB→EC2」の経路のうち、まだ無かった受け皿・案内・鍵を用意するため。famigo 側は0件変更・0件削除を毎回確認した。
🏢 たとえ：雑居ビル（EC2）の空き区画に新しい事務所を構えるにあたり、①ビル入口の受付（ALB）に「“Civil Track宛て”の来客はこの部屋へ」という案内札を1枚足し、②部屋のドアに「受付から来た人だけ入室可」の許可を貼り、③「civil-track.com」という看板（ドメイン）と本人証明（証明書）を用意した。既存テナント（famigo）の設備には一切触らない。

第2幕本番アプリ設定

＝ 同じアプリでも「本番用の顔」に整える

🎯目的：ローカル（自分のPC）で動く設定のまま本番に出すと危険・不都合。本番専用の設定を用意する。※これは事前にコードとして準備済みだった。
1

本番用の設定ファイルを用意

本番用の環境設定（.env.production の雛形）と、本番用の起動手順（Docker のファイル一式）を作成。エラー詳細を隠す・HTTPSでcookieを送る等、本番向けに調整。

なぜ：ローカル用は「エラーを画面に全部出す」など開発に便利な代わりに本番では危険な設定。分けておく必要がある。
2

「ALB越しでも正しく動く」設定を追加（TrustProxies）

ALB が HTTPS を受けて、EC2 へは HTTP で渡す構成。この一言設定が無いとアプリが「自分はHTTPだ」と勘違いし、ログインの cookie が壊れる等の不具合になる。

なぜ：ALB を挟む本番特有のハマりどころ。先回りして潰しておいた。
👔 たとえ：同じ人（アプリ）でも、社内（ローカル）ではラフな格好でよいが、来客対応（本番）ではスーツに着替える。さらに「受付(ALB)を経由して来た客への応対マナー」も仕込んでおいた。

第3幕デプロイ作業

＝ アプリを実際に EC2 へ運び込み、DBを用意して、動かす

🎯目的：用意した部屋（第1幕）に、本番仕様のアプリ（第2幕）を実際に設置して起動する。ここが一番細かい手数が多かった部分。
1

EC2 に入る手段を用意（SSM）

鍵なしで EC2 を遠隔操作できる仕組み(SSM)を使い、私がコマンドを送り込む方式で作業した。

なぜ：EC2 の中で「コードを置く・DBを作る・起動する」を行う必要があるため。
2

メモリ不足に備えて Swap を追加対策

EC2 のメモリが小さく（実質1GB弱）、famigo と同居させると足りなくなる恐れ。あふれた分の避難場所（Swap 2GB）を先に用意した。

なぜ：メモリ不足でアプリが強制終了し、famigo まで巻き添えで落ちるのを防ぐ保険。
3

アプリのコードを EC2 に配置

GitHub（公開リポジトリ）からソース一式をダウンロードし、EC2 の /opt/civil に展開。本番用の設定ファイル(.env.production)を作成。

なぜ：動かす実体（プログラム）を部屋に運び込む工程。

今回の手法：やっていること（GitHubからコードを持ってくる）は git clone と同じだが、今回は EC2 に git をインストールしていないため、コードを zip 相当に固めたファイル（tar.gz）を curl でダウンロードして展開する方法を取った。git は使っていない。

4

データベース(RDS)に置き場所を作った

共用の RDS の中に、Civil Track 専用の「棚（データベース）」と「鍵（専用ユーザー）」を新規作成。その後、アプリが必要とするテーブル一式を自動生成(migration)し、初期データ（事務所・管理者アカウント）を投入。

なぜ：データの保存先。famigo のデータとは棚を分け、専用ユーザーは自分の棚しか触れないようにした。
5

いくつかの本番特有のつまずきを解消対策

DB権限の不足(REFERENCES)、ビルド道具の古さ(buildx)、gitが未導入、起動失敗ループが裏でDBを汚す——といった想定外に順に対処した。

なぜ：本番環境はローカルと条件が違い、実際に動かして初めて分かる差異がある。原因を切り分けて回避策で通した。
6

コンテナを起動し、経路が開通したか確認

Nginx+PHP のコンテナを起動 → ALBのヘルスチェックが healthy に → https://civil-track.com でログイン画面が表示されることを確認。メモリも実測して famigo 無事を確認。

なぜ：「ブラウザ→ALB→EC2→RDS」が実際に一本つながったかの最終確認。
📦 たとえ：用意した部屋に、荷物（アプリ）を運び込み（3）、電源が足りるようブレーカーを増設し（2 Swap）、書類棚と鍵を用意して中身を並べ（4 DB）、搬入中のトラブルを片付けながら（5）、最後に照明をつけて「ちゃんと営業できる」ことを確認した（6）。

✅ 結果

https://civil-track.com で Civil Track が公開され、ログイン・動作確認まで完了。作業中、既存の famigo は一度も停止しなかった（無停止を最優先にした設計・対策が効いた）。
