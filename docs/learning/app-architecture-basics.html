1全体像（登場人物の地図）

ひとことで：ブラウザの依頼を、AWS の入口 → サーバーの中の2つのコンテナ → データの置き場 へと順に受け渡し、完成した HTML を同じ道で返している。

実線＝1回のページ表示で必ず通る道（番号は順番）。点線＝ブラウザが直接取りに行くもの・裏で流れるもの。オレンジ＝AWS のサービス、青・緑＝EC2 の中のコンテナ。

  1. DNS で「civil-track.com はどこ？」を調べ、最終的に Route53 が答える（途中の DNS サーバーは図では省略。4章）
  2. ALB に HTTPS でつなぎ、依頼を送る
  3. ALB が依頼を EC2 の 8081番（nginx コンテナ）へ回す
  4. nginx が PHP の処理を php コンテナ（PHP-FPM ＋ Laravel）へ頼む
  5. Laravel が RDS（MySQL）からデータを読み、HTML を組み立てる → 来た道を戻ってブラウザへ
たとえ：役所の窓口。Route53 は「〇〇課は何階？」に答える案内板、ALB は建物の正面受付（どの課の用事か見て振り分ける）、nginx は課のカウンター係（パンフレットならその場で渡し、相談なら奥へ回す）、Laravel は奥で書類を作る担当者、RDS は書庫、S3 は写真の保管庫です。

2前提：HTTP というやりとりの形

ひとことで：ブラウザとサーバーは「リクエスト（依頼）を1通送る → レスポンス（返事）が1通返る」を、ページを開くたびに何十回も繰り返している。

ブラウザとサーバーの会話は、すべて HTTP という決まった形式の手紙でやりとりされます。HTTPS は、その手紙を暗号化して送る版です。中身は実はただの文字です。

# ブラウザ → サーバー（リクエスト）
GET /requests?response_status[]=in_progress&department[]=road HTTP/1.1
Host: civil-track.com
Cookie: civil_track_session=eyJpdiI6...（ログインの合言葉）
Accept: text/html

# サーバー → ブラウザ（レスポンス）
HTTP/1.1 200 OK
Content-Type: text/html; charset=UTF-8
X-Request-Id: 3f1c9a2e-...（このアプリが付ける問い合わせ番号）
Set-Cookie: civil_track_session=...; secure; httponly

<!DOCTYPE html><html lang="ja"> ...（画面の中身）

リクエストの部品

  • メソッド：何をしたいか。GET＝見せて、POST＝登録して、PUT＝更新して、DELETE＝消して
  • パス：どのページか（/requests）
  • クエリ文字列：? の後ろ。検索条件など
  • ヘッダ：付属情報。Host（宛先のドメイン）、Cookie など
  • ボディ：POST で送るフォームの中身

レスポンスの部品

  • ステータスコード：結果の番号（下の表）
  • ヘッダ：中身の種類（Content-Type）、Cookie の発行（Set-Cookie）、移動先（Location）など
  • ボディ：HTML・CSS・画像などの本体

このアプリで出会うステータスコード

番号意味このアプリで起きる場面
200成功画面が普通に表示された
302別の場所へ移動してログイン後にダッシュボードへ／登録後に一覧へ／未ログインでログイン画面へ
403権限がない他部署の案件の編集画面を URL 直打ちで開こうとした（Policy が拒否）
404見つからない存在しない案件／一般職員が他事務所の案件 ID を指定した（事務所スコープで「無いもの」扱い）
419ページの有効期限切れ（Laravel 独自）フォームを開いたまま長時間放置してから送信した（CSRF トークン・セッション切れ）
422入力内容が不正入力チェックに引っかかった（画面ではリダイレクトして赤字のエラーを出す）
500サーバー内部のエラープログラムの想定外のエラー。問い合わせ番号（request_id）つきのエラー画面を出す
502〜504奥のサーバーが応答しないALB や nginx が出す。コンテナが止まっている、処理が時間切れ、など
🔑HTTP は「1往復で忘れる」仕組み。サーバーは、前のリクエストを誰が送ったのか覚えていません（ステートレス）。それでもログイン状態が続くのは、ブラウザが毎回 Cookie で「さっきの者です」と名乗っているからです（8章）。

31回の検索を追いかける

例：ログイン済みの職員が、案件一覧で「対応状況＝対応中」「対応部署＝道路」にチェックして［検索］を押す。

検索フォームは method="GET" なので、押した瞬間にブラウザは次の URL を開きに行きます。ここから画面が出るまでを、通る場所の順に追いかけます。

https://civil-track.com/requests?response_status[]=in_progress&department[]=road
  1. ブラウザ

    URL を分解し、送る準備をする

    https（暗号化して送る）・civil-track.com（宛先）・/requests（ページ）・?response_status[]=…（条件）に分けます。このサイト用に保存してある Cookie（civil_track_session など）を添えます。

  2. Route53（DNS）

    「civil-track.com はどこ？」を調べる

    インターネット上の住所は IP アドレス（数字）なので、名前を数字に変換します。PC は DNS サーバーを順にたどって Route53 にたどり着き、Route53 の エイリアス A レコードが「ALB の今の IP アドレス」を答えます。結果はしばらくブラウザや PC に記憶（キャッシュ）されるので、毎回聞くわけではありません（たどり方と実際の答えは 4章）。

  3. ALB（HTTPS の終端）

    暗号化の握手をして、中身を読む

    ブラウザは教えてもらった IP アドレスの 443番につなぎ、ALB との間で TLS ハンドシェイク（暗号の鍵を決める握手）をします。ALB は famigo 用と Civil Track 用の2枚の証明書を持っていて、ブラウザが最初に名乗るドメイン名（SNI）を見て civil-track.com の証明書（ACM が発行・自動更新）を出します。ここで暗号が解かれ、ALB は HTTP の中身を読めるようになります（HTTPS の順番・証明書の見方は 4章）。

    • http://（80番）で来た場合は、443番（https://）へリダイレクトさせます。
  4. ALB（振り分け）

    どちらのアプリ宛てか見て、EC2 の 8081番へ回す

    ALB は famigo と共有です。443 リスナーにホスト名が civil-track.com なら civil-request-tg-8081 へというルール（優先度100）を足してあり、それ以外は今までどおり famigo の 8080 番へ流れます。

    • ALB から EC2 へは暗号化しない HTTPで送ります（AWS の中の通信のため）。代わりに X-Forwarded-Proto: https などのヘッダで「元は HTTPS だった」と伝えます。
    • EC2 のセキュリティグループは、8081番を ALB からだけ通します。インターネットから直接 8081 にはつながりません（EC2 のほかの許可ルールは 4章）。
    • ALB は 30 秒ごとに /health を叩き、3回続けて失敗したらそのサーバーを「異常」として切り離します（ヘルスチェック）。
  5. EC2 → nginx コンテナ

    Docker が 8081番を nginx コンテナの 80番につなぐ

    docker-compose.prod.yml の ports: "8081:80" により、EC2 の 8081番に来た通信がコンテナの 80番へ渡ります（各番号の設定場所は 4章）。nginx は default.conf のルールで行き先を決めます。

    root /var/www/html/public;            # 公開してよいファイルの置き場
location / {
    try_files $uri $uri/ /index.php?$query_string;   # ① ファイルがあれば返す ② 無ければ index.php へ
}
location ~ \.php$ {
    fastcgi_pass php:9000;                # PHP の処理は php コンテナへ頼む
}

    /requests というファイルは無いので、/index.php に回されます。一方 /css/common.css は実在するので、nginx がその場で返します（PHP は動きません）。

  6. nginx → php コンテナ（FastCGI）

    「この PHP を実行して」と頼む

    nginx 自身は PHP を実行できません。FastCGI という取り決めで、php コンテナの 9000番で待っている PHP-FPM に依頼します。宛先の php はコンテナのサービス名で、同じ Docker ネットワーク（civil-network）の中では名前で相手を呼べます。

    PHP-FPM は PHP を実行する作業員（ワーカープロセス）を何人か待機させていて、空いている1人が public/index.php を実行します。リクエストが終わると、そのリクエスト用に作ったものはすべて捨てられます（PHP は毎回まっさらな状態から始まる）。

  7. Laravel：起動

    index.php → bootstrap/app.php でアプリを組み立てる

    Laravel は毎回、設定を読み、部品を用意し、ルートを登録します。本番では起動時（entrypoint.prod.sh）に config:cache・route:cache・view:cache を済ませているので、毎回の組み立ては1つのファイルを読むだけで速く終わります。

  8. Laravel：ミドルウェア（関所）

    コントローラに届く前に、順番にチェックを通る

    • TrustProxies：ALB が付けた X-Forwarded-Proto を信じ、「自分は HTTPS で動いている」と認識する（これが無いと、作るリンクが http:// になる）
    • TraceRequest（自作）：このリクエストの問い合わせ番号（request_id）を決める。以降のログ行に自動で付く
    • セッション開始：Cookie の番号から、サーバーに保存したセッションファイルを読み込む
    • CSRF チェック：POST などの書き込み系だけ。GET の検索では素通り
    • auth：ログインしていなければ、ここで /login へ 302 リダイレクト
    • force.password.change（自作）：初期パスワードのままならパスワード変更画面へ
  9. Laravel：ルーティング

    URL から担当のコントローラを決める

    Route::get('/requests', [RequestController::class, 'index'])->name('requests.index');

    routes/web.php の対応表で「GET /requests は RequestController の index」と決まります。

  10. Laravel：FormRequest（入力チェック）

    検索条件が正しい値か確かめる

    index(SearchRequestRequest $request) と書くだけで、コントローラの中身が動く前に SearchRequestRequest のルールで検査されます。response_status に in_progress のような決まった値以外が入っていれば、ここで弾かれます。

  11. Laravel：コントローラ → モデル

    検索条件を SQL にして、RDS に問い合わせる

    $requests = RequestSearch::query($filters, $isAdmin)   // 条件を組み立てる（app/Support）
    ->with('office')                                 // 事務所名もまとめて取る
    ->paginate(self::PER_PAGE);                       // 1ページ分だけ取る

    Eloquent（Laravel の DB 係）が、PHP のコードを SQL に翻訳します。ここで、Request モデルに付けてある OfficeScope が、一般職員なら自動で「自分の事務所だけ」の条件を足します。

    select * from requests
 where response_status in (?) and department in (?)
   and requests.office_id = ?        -- ← OfficeScope が自動で足す
   and requests.deleted_at is null   -- ← SoftDeletes が自動で足す（削除済みを除く）
 order by reception_date desc, reception_time desc
 limit 20 offset 0

    php コンテナは RDS の 3306番に接続して SQL を送ります。RDS はパブリックアクセス不可で、セキュリティグループで EC2 からの 3306番だけを受け付けます。? の部分には値が別送りで入るので、入力値が SQL として実行されることはありません（SQL インジェクション対策。プリペアドステートメント）。

  12. Laravel：Blade（画面を組み立てる）

    データを HTML のひな形に流し込む

    コントローラは view('requests.index', [...]) で、取れた案件を resources/views/requests/index.blade.php に渡します。Blade は共通レイアウト（layouts/app.blade.php：ヘッダー・メニュー）に、一覧の表を差し込んで、1枚の完成した HTML にします。

    • {{ $value }} で出した値は自動でエスケープされます（<script> のような文字が入っていても、ただの文字として表示される。XSS 対策）。
    • メニューの「新規登録」「ユーザー管理」は @can で、権限がある人にだけ HTML に出します。
  13. php → nginx → ALB → ブラウザ

    完成した HTML を来た道で返す

    レスポンスには X-Request-Id ヘッダが付きます。処理が終わった直後に、TraceRequest がアクセスログを1行出します（メソッド・パス・ステータス・処理時間。検索語が入りうるクエリ文字列は出さない）。nginx も自分のアクセスログを1行出し、どちらも CloudWatch に送られます。

  14. ブラウザ

    HTML を読みながら、足りない部品を追加で取りに行く

    HTML の中に書かれた <link> や <script> を見つけるたびに、それぞれ別のリクエストを送ります。

    • /css/common.css?v=1730…：nginx が直接返す（?v= は更新日時。CSS を直したら番号が変わり、古いキャッシュを使わせない仕組み＝versioned_asset()）
    • Google Fonts の CSS とフォントファイル：Google のサーバーから直接

    すべてそろうと、画面が完成します。ここまでで、だいたい数百ミリ秒です。

✅まとめると、HTML 1枚のために動くのは「Route53 → ALB → nginx → PHP-FPM → Laravel → RDS」。CSS・画像・フォントは別のリクエストで、そのほとんどは PHP まで届かず nginx や外部サーバーが返しています。

4入口の通信を詳しく（DNS・HTTPS・証明書・門番・ポート）

ひとことで：名前を IP に変え、暗号化してつなぎ、門番を通り、番号（ポート）を頼りにコンテナまで届く。その一つひとつが、どこで設定されているかを見ていく。

DNS：Route53 にたどり着くまで

ブラウザが最初から Route53 の場所を知っているわけではありません。アプリのコードにも「Route53 へ行く」とは書かれていません。インターネット共通の DNS の仕組みで、次のように順にたどります。

ブラウザ・PC              覚えていれば、それを使って終わり
  ↓
自宅ルーターなど
  ↓
プロバイダ等の DNS サーバー 代わりに調べてくれる係
  ↓
ルート DNS                「.com の担当はあちらです」
  ↓
.com の DNS               「civil-track.com の担当は ns-1403.awsdns-47.org などです」
  ↓
Route53                   「IP アドレスはこれです」

Route53 に直接問い合わせると、次の答えが返ります（2026-11-23 に確認した値）。

名前              タイプ  TTL   IP アドレス
civil-track.com   A       60    3.114.175.58
civil-track.com   A       60    54.178.253.11
  • TTL 60：「この答えは60秒間覚えていて構いません」という意味
  • IP が2つ：ALB が2つのアベイラビリティゾーン（1a・1c）にいるため
  • IP は変わる：11/18 に調べたときは 54.95.241.127 などでした。ALB の IP は固定ではないので、IP を直接書かず、ALB を指すエイリアスにしています
  • Route53 のコンソールの「値/トラフィックのルーティング先」には ALB の名前が表示されますが、問い合わせへの返事は ALB の今の IP です
何をどこで決めているか
Route53 に置く内容（ALB を指す A レコード）infra/route53.tf（Terraform）
「このドメインの担当は Route53」という登録（NS）ドメインを取得したレジストラの設定

HTTPS：ALB につなぐ順番

  1. 接続：DNS で分かった IP アドレスの 443番につなぐ
  2. TLS の握手：「civil-track.com に用があります」（SNI）と伝え、ALB が出した証明書を確認して、暗号の鍵を決める
  3. HTTP を暗号化して送る：下の内容が、暗号の中に入って届く
GET /requests HTTP/1.1
Host: civil-track.com
Cookie: civil_track_session=...

IP アドレスは「届け先」にだけ使い、ドメイン名は SNI と Host ヘッダで別に伝えます。SNI は「どの証明書を出すか」、Host は「どのアプリへ回すか」の判断に使われるので、同じ IP でも famigo と Civil Track を見分けられます。

⚠️IP アドレスを直接入力しても、Civil Track のログイン画面には来ません。SNI が無いので ALB はデフォルトの famigo の証明書を出し、ブラウザは名前が合わないと警告します。警告を無視して進んでも、Host が civil-track.com ではないのでルールに当たらず、famigo 側へ流れます。

証明書：名前がたくさんあるが、実物は2枚

コンソールに出てくる証明書の名前は、このアプリではすべて ACM が発行したサーバー証明書のことです（2枚とも種類は AMAZON_ISSUED）。名前の違いは、証明書の種類ではなく「どこに置いてあるか・ALB がどの場面で使うか」の違いです。

名前立場今の設定
ACM の証明書証明書の本体（発行・保管・更新）api.famigo-odekake.com、civil-track.com の2枚
デフォルトの SSL/TLS 証明書ALB の設定。名前が分からない・一致しないときに出す1枚famigo
リスナー証明書（SNI）ALB の設定。SNI の名前で選ぶ候補の一覧famigo、civil-track
たとえ：ACM は証明書をしまう金庫、ALB の設定は「このお客さんにはこれを見せる」という担当表。famigo の証明書は担当表の「デフォルト」と「SNI の一覧」の両方に載っているので画面では3行に見えますが、実物は2枚です。

ACM で本体を見る

  1. コンソール右上のリージョンを東京にする
  2. 検索欄に Certificate Manager と入力して開く
  3. 左メニューの証明書を一覧表示を開く
  4. ドメイン名をクリックすると、状態・有効期限などが見られる

ALB での使われ方を見る

  1. EC2 → 左メニューのロードバランサー
  2. famigo-alb を選ぶ
  3. リスナーとルール → HTTPS:443
  4. 証明書のタブを開く

証明書の中身は、ブラウザで https://civil-track.com を開き、アドレスバー左のアイコンからも確認できます。証明書を出すのは ALB なので、EC2 が停止中で 503 の画面でも見られます。なお一般には、他社で発行した証明書を ACM に持ち込むこともでき、その場合の種類は IMPORTED になります。

セキュリティグループ：3段の門番

ALB・EC2・RDS に1つずつ門番が付いていて、それぞれ「誰からの、何番への通信を通すか」を決めています。

インターネット
  │ 80 / 443 は誰でも可
  ▼
famigo-sg-alb（ALB）
  │ 8080 / 8081 は ALB からだけ可
  ▼
famigo-sg-ec2（EC2）
  │ 3306 は EC2 からだけ可
  ▼
famigo-sg-rds（RDS）

EC2 の門番の受信ルールは、実際には次の3つです。

ポート許可する相手用途
8080ALB のセキュリティグループfamigo
8081ALB のセキュリティグループCivil Track（infra/security_group.tf で追加）
22登録された1つの IP アドレスSSH（既存のルール。Civil Track の作業は SSM を使う）

許可する相手に IP アドレスではなくセキュリティグループそのものを指定しているので、ALB の IP が変わっても設定を直す必要がありません。一覧に default という名前が見える場合、それは VPC に自動で作られるもので、ALB・EC2・RDS では使っていません。

ポート：各番号はどこで設定しているか

ポートは、1つのコンピュータやコンテナの中で「どのプログラム宛てか」を区別する番号です。IP アドレスが建物の住所なら、ポートは部屋番号にあたります。

区間書いてある設定場所
ALB → EC2 の 8081port = var.app_portinfra/target_group.tf
上の変数の中身default = 8081infra/variables.tf
EC2 の 8081 → nginx の 80"8081:80"（左が EC2、右がコンテナ）docker-compose.prod.yml
nginx が 80 で待つlisten 80;docker/nginx/default.conf
nginx → php の 9000fastcgi_pass php:9000;同じ default.conf
PHP-FPM が 9000 で待つlisten = 9000PHP 公式イメージの中の /usr/local/etc/php-fpm.d/docker.conf（このリポジトリには無い）
  • var.app_port は Terraform の変数です。ターゲットグループの名前・転送先ポート・EC2 の登録・セキュリティグループの許可で同じ変数を使っているので、番号を変えるときは variables.tf の1か所で済みます
  • php:9000 の php は Compose のサービス名で、Docker が同じネットワーク内の php コンテナに変換します
  • php には ports: の指定がないので、外からは届かず、同じネットワークの nginx からだけ届きます

7サーバーで HTML を作る方式（SPA との違い）

ひとことで：このアプリは、クリックのたびにサーバーが「1ページ丸ごと」作って返す方式。React などの SPA ではない。

サーバーサイドレンダリング（このアプリ）

Laravel ＋ Blade

  • サーバーが HTML を完成させて返す
  • リンクやボタンを押すと、ページ全体が切り替わる
  • 作るのは「画面を返すサーバー」1つだけ
  • JavaScript が少なくて済む。検索結果の URL をそのまま共有・ブックマークできる

SPA（シングルページアプリケーション）

React・Vue など＋ API

  • 最初に JavaScript のアプリを丸ごと読み込む
  • 以降はデータ（JSON）だけを取りに行き、ブラウザ側で画面を描き替える
  • 「画面側のアプリ」と「API サーバー」の2つを作る必要がある
  • 画面遷移がなめらか。地図や表計算のような、操作が多い画面に向く

このアプリは「入力フォーム・検索・一覧」が中心の業務システムで、ページ単位で切り替わっても困らないため、構成をシンプルに保てるサーバーサイドレンダリングを選びました（README の選定理由）。

⚠️Vite・Tailwind の設定ファイルは残っているが使っていない。resources/js/app.js や package.json は Laravel の初期状態のまま残っているもので、画面は public/css/common.css と各画面の <script> だけで動いています（ビルド不要）。

8ログインの状態をどう覚えているか

ひとことで：サーバーにメモ（セッション）を残し、ブラウザにはそのメモの番号札（Cookie）だけを渡す。

  1. ログイン画面で［ログイン］

    ID とパスワードを POST で送る

    AuthController@login が、ID を小文字にそろえ、Auth::attempt() で「有効な（status=active）アカウントで、パスワードが合うか」を確かめます。DB にはパスワードそのものではなく、ハッシュ（元に戻せない変換をした値）が入っていて、入力値を同じように変換して比べます。

  2. 成功

    セッションを作り直し、番号札を渡す

    session()->regenerate() でセッション ID を新しくします（ログイン前の ID を盗まれていても使えなくする＝セッション固定攻撃の対策）。サーバーの storage/framework/sessions/ に「この番号の人はユーザー○番」と書いたファイルを置き、ブラウザには Set-Cookie: civil_track_session=… で番号札を渡します。

    • Cookie は secure（HTTPS のときだけ送る）・httponly（JavaScript から読めない）の設定
    • 何も操作しないまま 120分たつと、セッションは期限切れ（SESSION_LIFETIME=120）
  3. 以降のすべてのリクエスト

    ブラウザが毎回 Cookie を添える → ミドルウェアが本人を特定

    セッション開始のミドルウェアが番号からファイルを読み、auth()->user() で「今の操作者」が分かるようになります。OfficeScope や Policy は、この情報を使って判断しています。

  4. 初回ログインのとき

    パスワード変更を強制する

    users.must_change_password が true の間は、ForcePasswordChange ミドルウェアが、パスワード変更とログアウト以外の画面をすべて変更画面へリダイレクトします。

CSRF 対策（なりすまし送信を防ぐ）

Cookie はブラウザが自動で送るので、悪いサイトに仕込まれたフォームから「勝手に削除ボタンを押した」ことにされる危険があります（CSRF）。Laravel はフォームに @csrf でそのページを開いた人だけが知っている合言葉（トークン）を埋め込み、POST・PUT・DELETE のときに照合します。合わなければ 419 エラーになります。

たとえ：Cookie は会員証、CSRF トークンはその日の整理券。会員証だけでは窓口の手続きはできず、受付で渡された整理券も一緒に出す必要がある。
⚠️セッションはコンテナの中のファイル。本番は SESSION_DRIVER=file で、php コンテナの中に保存しています。デプロイでコンテナを作り直すとファイルが消えるので、デプロイすると全員ログアウトされます。利用の少ない時間に手動デプロイする運用で受け入れています（台数を増やすなら、DB や Redis に保存する方式に変える必要がある）。

9登録ボタンを押したとき（POST の流れ）

ひとことで：POST で送る → 検査 → 保存 → 「一覧へ移動して」と返す（PRG パターン）。

POST /requestsフォームの中身をボディに入れて送る
→
CSRF・権限合言葉と、登録できる人か
→
StoreRequestRequest必須・形式・選択肢の検査
→
保存トランザクションで採番＋INSERT
→
302 → GET /requests一覧で「登録しました」

入力に誤りがあったとき

FormRequest の検査で引っかかると、コントローラは動かず、元のフォームへリダイレクトされます。このとき入力した値（old()）とエラーメッセージ（@error）を一時的にセッションに入れて渡すので、入力し直さずに赤字の箇所だけ直せます。

受付番号の採番（同時に押されても重ならない）

DB::transaction(function () {
    $maxSeq = Request::withTrashed()                       // 論理削除した番号も数える
        ->withoutGlobalScope(OfficeScope::class)
        ->where('office_id', $officeId)->where('reception_year', $year)
        ->lockForUpdate()                                  // 終わるまで他の人を待たせる
        ->max('reception_seq');
    // 最大値 + 1 で "2026-0028" のような番号を作って保存
});

「今の最大番号を読む → +1 して保存」の間に別の人が同じことをすると、同じ番号ができてしまいます。トランザクション＋行ロックでその間を一人ずつにし、最後の守りとして DB の UNIQUE 制約も置いています。

なぜ保存後に「移動して」と返すのか（PRG）

POST の結果をそのまま画面として返すと、ブラウザの再読み込みで同じ POST がもう一度送られ、二重登録になります。保存後は 302 で一覧（GET）へ移動させることで、再読み込みしても一覧を開き直すだけになります。これを Post / Redirect / Get パターンと呼びます。

🔑HTML のフォームは GET と POST しか送れない。更新（PUT）や削除（DELETE）のフォームでは、@method('PUT') で隠し項目 _method=PUT を入れて POST で送り、Laravel が「本当は PUT」と読み替えています。

保存（アップロード）

  • ブラウザ → nginx → Laravel にファイルが届く（上限は nginx と PHP の設定で決めている）
  • Laravel が入力チェック（画像か、サイズは大丈夫か）

11コンテナと Docker Compose

ひとことで：「動かすのに必要なもの一式」を箱（イメージ）に詰め、どこでも同じように動かす仕組み。Compose は複数の箱をまとめて動かす指示書。

イメージ
コンテナの元になる「型」。OS の一部・PHP・拡張・アプリのソースなどが入っている。Dockerfile に作り方を書く
コンテナ
イメージから起動した「実物」。止めて作り直すと、中で書き込んだものは消える
ネットワーク
コンテナ同士をつなぐ専用の線。同じネットワークならサービス名（php）で相手を呼べる
ポート公開
"8081:80"＝EC2 の 8081番をコンテナの 80番につなぐ。php は公開せず、nginx からしか届かない
ボリューム
コンテナの外に置く保存場所。作り直しても消えない（ローカルの MySQL のデータなど）

本番のイメージの作り方

php（docker/php/Dockerfile.prod）

  • php:8.3.36-fpm を元にする（脆弱性対応のため細かい版まで固定）
  • MySQL 接続・画像処理などの PHP 拡張を入れる
  • composer install --no-dev で、本番に必要なライブラリだけ入れる
  • アプリのソースをイメージの中にコピー（焼き込む）

nginx（docker/nginx/Dockerfile.prod）

  • nginx:1.30.6-alpine を元にする
  • 設定ファイル default.conf を入れる
  • public/ だけをコピー（静的ファイルを自分で返すため）

php コンテナが起動するとき（entrypoint.prod.sh）

php artisan migrate --force   # DB のテーブルを最新の形にする（足りない変更だけ）
php artisan config:cache      # 設定を1ファイルにまとめる（以降 .env は読まない）
php artisan route:cache       # ルート表をまとめる
php artisan view:cache        # Blade を PHP に変換しておく
exec php-fpm                  # ここから PHP-FPM が依頼を待ち始める
✅famigo との分離。Civil Track は専用のネットワーク（civil-network）・専用の Compose ファイル（-f docker-compose.prod.yml）・専用のポート（8081）を使います。同じ EC2 の上にいても、famigo のコンテナとは直接つながらず、Civil Track のデプロイで famigo を巻き込みません。異常終了したときは restart: unless-stopped で自動的に再起動します。

13画面に出ない裏方の仕組み

ひとことで：作るとき（CI・テスト）、置くとき（デプロイ・Terraform）、動いている間（ログ・監視）を支える仕組み。

ログと監視

動いている間の見張り役

コンテナの出力を Docker（awslogs ドライバ）が CloudWatch Logs の /civil/app へ送ります。ERROR のログ・サイト停止・ディスク逼迫でアラームが鳴り、SNS がメールで知らせます。詳しくは ログと監視の基礎。

CI（GitHub Actions）

作るときの安全網

PR を出すたびに、Pint（整形）・PHPStan（静的解析）・PHPUnit（テスト）を GitHub 上で自動実行します。本番への自動デプロイ（CD）はしていません。詳しくは CI の基礎・テストの基礎。

デプロイ（手動）

新しい版を本番に置く

SSM で EC2 に入り、/opt/civil で最新のソースを取得 → docker compose -f docker-compose.prod.yml up -d --build でイメージを作り直して起動。起動時に entrypoint がマイグレーションを流します。詳しくは デプロイ振り返り（技術版）。

Terraform

AWS の設定をコードで残す

Civil Track のために追加した AWS リソース（証明書・Route53 のレコード・ALB のリスナールール・写真用の S3・CloudWatch のロググループやアラーム・SNS など）を infra/ のコードで管理します。famigo の既存リソースは読み取るだけで、手を加えません。

14困ったとき、どこを見るか

ひとことで：「どこまで届いたか」で原因の場所を絞る。1章の地図を上から順にたどるのが近道。

症状止まっている場所の候補まず見るもの
名前が見つからない（DNS のエラー）DNSnslookup civil-track.com で IP が返るか。Route53 のレコード、レジストラの NS 設定
証明書の警告が出るURL の間違い・証明書IP アドレスで開いていないか。ACM の状態と ALB の証明書の設定
502 / 503（ALB の画面）ALB の先のサーバーが応答しない。EC2 を止めている間は 503（DNS と ALB は動いている）EC2 が起動しているか（普段は止めている）。ターゲットグループのヘルスチェックが healthy か。docker ps でコンテナが動いているか
504処理が時間切れ重い処理・DB の応答。CloudWatch の php のログ
500（問い合わせ番号つきの画面）Laravel の中のエラー。RDS だけ止まっている場合も、DB を使う画面はここ画面の番号（request_id）で CloudWatch Logs を検索し、ERROR の行を見る。RDS が起動しているか（/health は DB を見ないので、RDS だけ止まっていても ALB は healthy のまま）
画面は出るが見た目が崩れるCSS が届いていないブラウザの開発者ツール（F12）の Network タブで common.css が 200 か
地図だけ出ないLeaflet か国土地理院のタイル開発者ツールの Console のエラー、タイル画像のリクエスト。ピンだけ出ないなら /map/pins の応答
写真だけ出ないS3・署名付き URL・IAM ロール画像の URL が 403 になっていないか（期限切れ・権限）
ログインしてもすぐログイン画面に戻るCookie が保存されない・送られないHTTPS で開いているか（secure Cookie）、TrustProxies の設定
419セッション切れ・CSRFページを開き直してから送信し直す。デプロイ直後なら全員ログアウトされている
🔑ブラウザの開発者ツールは最初の味方。F12 → Network タブを開いてから操作すると、1回のページ表示で何本のリクエストが飛び、どれが何番で返ったかが一覧で見えます。3章で見た「HTML 1本＋CSS・フォント・地図・写真の別リクエスト」を、自分の目で確かめてみてください。

15用語ミニ辞典

DNS
ドメイン名（civil-track.com）を IP アドレスに変換する仕組み。Route53 が担当
ネームサーバー（NS）
そのドメインの DNS の答えを持っているサーバー。このアプリでは Route53 の ns-1403.awsdns-47.org など4つ
エイリアスレコード
Route53 独自の機能。ALB などの AWS リソースを名前で指定すると、その時点の IP を答えてくれる
TTL
DNS の答えを覚えていてよい秒数
ポート
1つのコンピュータやコンテナの中で、どのプログラム宛てかを区別する番号
TLS / HTTPS
通信を暗号化する仕組み／それを使った HTTP。証明書で相手が本物か確かめる
SNI
暗号化の握手の最初に「どのドメインに用があるか」を伝える仕組み。1つの ALB で複数の証明書を使い分けられる
デフォルト証明書
SNI の名前が無い・一致しないときに ALB が出す証明書。このアプリの ALB では famigo のもの
ロードバランサー
入口で通信を受け、後ろのサーバーに振り分ける装置。ALB は HTTP の中身（ホスト名・パス）で振り分けられる
ターゲットグループ
ALB の振り分け先のまとまり。ヘルスチェックの設定もここ
リバースプロキシ
利用者の代わりに奥のサーバーへ取り次ぐ役。ALB や nginx がこれにあたる
FastCGI
Web サーバーが、PHP などの実行役に処理を頼むときの取り決め
PHP-FPM
FastCGI で依頼を受けて PHP を実行するプログラム。作業員を何人か待機させる
フレームワーク
アプリの骨組みと定番の部品をまとめたもの。Laravel
ミドルウェア
コントローラの前後で、すべて（または一部）のリクエストに共通の処理をはさむ仕組み
MVC
Model（データ）・View（画面）・Controller（指揮）に役割を分ける考え方
ORM（Eloquent）
テーブルを PHP のクラスとして扱い、SQL を書かずに DB を操作できる仕組み
グローバルスコープ
モデルの検索すべてに自動で足される条件。OfficeScope・SoftDeletes
論理削除
行を消さず、deleted_at に日時を入れて「削除済み」扱いにすること
トランザクション
複数の DB 操作を「全部成功か、全部なかったことに」する仕組み
セッション
サーバー側に保存する、利用者ごとのメモ。ログイン状態など
Cookie
ブラウザが保存し、同じサイトへのリクエストに毎回添える小さなデータ
CSRF
他のサイトから、ログイン中の利用者になりすまして送信させる攻撃。トークンで防ぐ
XSS
入力欄に仕込んだスクリプトを、他の人の画面で実行させる攻撃。出力時のエスケープで防ぐ
SQL インジェクション
入力値で SQL の意味を書き換える攻撃。プリペアドステートメント（値の別送り）で防ぐ
署名付き URL
「この URL は期限まで有効」という署名を付けた URL。非公開の S3 のファイルを一時的に見せられる
IAM ロール
AWS のサービス（EC2 など）に付ける権限のセット。キーを置かずに S3 などを操作できる
イメージ／コンテナ
アプリを動かす一式の「型」／そこから起動した「実物」
マイグレーション
テーブルの作成・変更を PHP のコードで書き、順番に DB へ反映する仕組み
ステートレス
前のやりとりを覚えていないこと。HTTP や PHP の1リクエストはこの性質を持つ
