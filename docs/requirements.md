## 1. システム概要

### 1.1 背景・目的

地方の土木事務所では、道路・河川・砂防施設等の土木インフラに関する苦情・要望を、窓口・電話・メール・要望書など複数の手段で日々受け付けている。また、職員のパトロールによって発見される施設の異常箇所も別途対応が必要となる。

現状、これらの情報が一元管理されておらず、以下のような課題が想定される。

- 受付情報が担当者・部署ごとに分散し、全体像の把握が困難
- 対応状況（未対応／対応中／対応完了）の進捗管理が煩雑
- 過去の要望・対応履歴の検索・参照に時間がかかる
- 要望箇所の地理的な偏在や傾向の分析ができない

本システムは、これらの苦情・要望・異常箇所情報を一元管理し、受付から対応完了までの進捗を可視化することで、業務の効率化と対応品質の向上を図ることを目的とする。

### 1.2 システム化の対象範囲

- 対象施設：道路（橋梁・トンネルを含む）、河川、砂防施設
- 対象事案：住民等からの苦情・要望、および職員パトロールによる異常発見

### 1.3 想定利用者・権限方針

- 土木事務所内の全職員が、自事務所の全案件を閲覧できることを基本とする（部署を横断して状況を把握できる点に意味がある）
- 編集・削除（対応状況の更新、対応方針の登録等）は、案件の対応部署に応じた担当者のみ可能とする（道路案件は道路担当、河川案件は河川担当が編集）
- 新規登録（受付担当・パトロール担当）は、担当部署によらず職員であれば誰でも可能とする
- 利用は事務所内に閉じたクローズドな環境であり、A事務所の一般職員がB事務所の案件を閲覧することはない前提のため、ID・パスワードによるログイン認証は必須とする（詳細は「4.1 セキュリティ・個人情報保護」参照）
- 事務所ごとのデータ分離方式：単一システム上でユーザーアカウントに「所属事務所」を紐づけ、ログイン時にシステム側が所属事務所を自動判定する方式とする（事務所ごとにURL・インフラを分離する方式は採らない）。既存RDSへの相乗りにより追加コストを抑える方針（4.3参照）とも整合する
- 権限区分は「一般職員」「システム管理者」の2種類とする
  - **一般職員**：特定の事務所に所属し、自事務所の案件のみ閲覧・登録できる。編集・削除は対応部署が一致する案件のみ
  - **システム管理者**：特定の事務所に所属しない全体管理ロール。事務所ごとに配置するものではなく、システム全体で1〜数名を想定する。全事務所のユーザーアカウントの登録・編集・無効化（異動・退職時）を行える。また、個人情報の混入や不適切な記載など是正が必要な案件に対応するため、全事務所の案件を担当部署によらず閲覧・編集・削除できる
- ユーザーアカウントは職員本人による新規登録は行わず、システム管理者が発行する

## 2. 機能要件

### 2.1 苦情・要望・異常箇所の登録／削除／修正

- 窓口・電話・メール・要望書・FAX・職員パトロール・その他など、受付経路によらず同一の仕組みで登録できること
- 登録済みデータの修正・削除ができること（削除は論理削除とする）
- 変更履歴（誰が・いつ・何を変更したか）の保持は必須要件としない。ただし、案件ごとに「最終更新日時」を表示すること
  - ※ これは案件そのものの項目変更を監査ログとして残す機能を指す。対応の経過を記録する「2.6 対応履歴」とは別物であり、矛盾しない

### 2.2 属性データの登録・削除・修正・閲覧

「3. 登録項目」に定める属性データについて、登録・修正・削除・閲覧ができること。

### 2.3 任意条件検索

以下のような条件を組み合わせた検索ができること（項目間はAND条件を基本とする）。

- 受付日時（期間指定）
- 対応部署（複数選択可。例：「道路」「河川」を選ぶと、いずれかに該当する案件を検索対象とする＝選択項目内はOR条件）
- 対応状況（複数選択可。対応部署と同様に項目内はOR条件）
- 緊急性（複数選択可。対応部署と同様に項目内はOR条件）
- 地区・場所（住所の一部一致検索）
- キーワード（要望内容の検索。実装は部分一致検索。[データベース設計書 5章](database-design.md#5-今後検討すること)参照）

> 地図上の範囲指定検索（地図でエリアを囲んで絞り込む）は今回のスコープ外とする。住所の一部一致・各種条件（対応部署・対応状況・緊急性・期間・キーワード）による絞り込みで運用上の検索要件は満たせるため、必要になった時点で緯度経度の範囲指定として別途追加を検討する（[データベース設計書 5章](database-design.md#5-今後検討すること)参照）。

検索結果は一覧表示し、一覧から詳細画面への遷移、CSV出力ができること。地図表示画面（2.4参照）でも同一の検索条件を適用できること。

### 2.4 地図表示

- 要望・異常箇所を地図上にピン等で可視化する
- 地図上のピンから詳細情報を参照できる
- 検索結果を地図上にフィルタ表示できる

### 2.5 ユーザー管理・認証

- ID・パスワードによるログイン認証を必須とする（「1.3 想定利用者・権限方針」「4.1 セキュリティ・個人情報保護」参照）
- ユーザーアカウントの発行はシステム管理者が行う（職員本人による新規登録は不可）。システム管理者は全事務所のユーザーを横断して登録・編集・無効化できる
- ユーザー登録時に、氏名・ユーザーID・権限区分（一般職員／システム管理者）・初期パスワードを設定する。権限区分が「一般職員」の場合のみ、所属事務所・担当部署（道路／河川／砂防）もあわせて設定する（システム管理者は事務所に紐づかないため設定不要）
- パスワード変更ができること。初回ログイン時（初期パスワードのままログインした場合）は変更を必須とし、それ以降は任意のタイミングで変更できること
- システム管理者は、登録済みユーザーの氏名・ユーザーID・所属事務所・担当部署・権限区分を編集できること（入力ミスの訂正、異動に伴う所属事務所の変更等を想定）。異動時に所属事務所を変更した場合、当該ユーザーが以前の事務所で登録・編集した案件は登録時点の事務所に残り、異動後は新しい事務所の案件のみが閲覧・編集対象になる
- システム管理者は、異動・退職等に伴うアカウントの無効化ができること

### 2.6 対応履歴

要件定義書 §1.1 の課題「過去の要望・対応履歴の検索・参照に時間がかかる」に対応する機能。`response_status`（対応状況）は単一の現在値のみを保持するため、誰がいつ何を対応したかの経過は別途記録する。

- 案件ごとに、対応日・対応内容（自由記述）・記録者を複数回記録できる（タイムライン形式）
- 記録できる権限は、案件の編集権限と同一とする（対応部署が一致する一般職員、またはシステム管理者）。対応履歴は案件対応そのものであり、編集権限と異なる基準にすると部署を横断した書き込みが生じるため
- 他部署の職員は閲覧のみ可能
- 登録済みの対応履歴は内容を訂正できる（編集機能）。誤記録があった場合に訂正できないと記録が事実と異なってしまうため。ただし記録者（誰が記録したか）は訂正後も変更されない
- 訂正があった履歴には「編集済み」である旨と訂正日時を表示し、記録の訂正を隠さない
- 削除は論理削除とする（編集機能自体の履歴は持たない）
- 対応履歴の記録（追加・編集・削除）により、案件の「最終更新日時」（2.1参照）も更新される

### 2.7 進捗ダッシュボード

要件定義書 §1.1 の課題「対応状況の進捗管理が煩雑」に対応する機能。ログイン後のトップ画面とする。

- 対応状況別・緊急性別・対応部署別の件数を表示する。対応部署×対応状況のマトリクスも表示する
- 「未対応かつ緊急性『高』」「30日以上動きなし」を要対応サマリーとして最上部に表示する
  - 「動きなし」は**対応完了以外で、最後に対応した日から30日以上経過したもの**とする。「最後に対応した日」は最新の対応履歴の対応日（2.6）とし、対応履歴が一件も無い案件は受付日を起点とする
  - 案件レコードの最終更新日時（2.1）は用いない。対応履歴が無くても住所や対応方針を修正しただけで更新されてしまい、「受付から一切対応が進んでいない案件」を取りこぼすため
- 「対応を急ぐ案件」（緊急性「高」かつ未対応、または30日以上動きなし）を上位10件リスト表示する
  - 見出しは対応状況の値である「未対応」と混同されないよう、ステータス名と重ならない表記とする。「対応中」でも動きが止まっていれば対象になるため、特定のステータスを指す名称は使わない
  - 抽出条件はリストの直前（見出しの直下）に注釈として明示する。条件が自明でないため、リストを見る前に目に入る位置に置く
- 一般職員は自事務所の案件のみが集計対象（2.1のスコープと同一）。システム管理者は全事務所が対象となり、事務所別の内訳も追加表示される
- 各件数は該当条件で絞り込んだ案件一覧へのリンクとする（2.3の検索条件を再利用する）

### 2.8 現場写真

現場の状況は文章だけでは伝わりにくく、対応の前後で何が変わったかを後から確認できるよう、案件に写真を登録できるようにする。

- 写真は「いつの時点の写真か」が分かるよう、**対応履歴（2.6）に紐づけて登録する**。対応履歴の追加時・編集時に一緒に登録できる
- 要望者から提供された写真など、特定の対応に紐づかない写真は「受付時の写真」として案件に直接登録する
- 枚数の上限は**対応履歴ごとに5枚**、受付時の写真も5枚とする。案件合計での上限は設けない（対応が長期化して履歴が重なったときに、後の対応で写真を登録できなくなり現場の運用に合わないため）
- 形式は JPEG・PNG のみ、1ファイル5MBまでとする。形式はファイル名の拡張子ではなく中身で判定する（SVG はスクリプトを埋め込めるため、拡張子を偽装しても受け付けない）
- 登録・削除できる権限は対応履歴と同一（対応部署が一致する一般職員、またはシステム管理者）。他部署の職員は閲覧のみ可能
- 写真は公開URLを持たない非公開の保存領域に置き、一定時間（30分）のみ有効な署名付きURLで表示する。URLが外部に漏れても、期限が切れれば閲覧できない
- 写真の削除は物理削除とする（保存したファイルも消す）。誤登録や個人情報の写り込みを取り除くための操作であり、痕跡を残すと削除の目的を果たせないため
- 対応履歴を削除（論理削除）しても、その履歴の写真は削除しない（履歴と同じく痕跡を残す）。削除済みの履歴は表示されないため、その写真も表示されない
- 写真の登録・削除により、案件の「最終更新日時」（2.1参照）も更新される

## 3. 登録項目（属性データ）

個人情報を極力扱わない方針とし、相手方情報は「区分」「要望者」の2項目に絞る。

| 分類 | 項目 | 備考 |
|---|---|---|
| 管理情報 | 受付番号 | 一意なID。自動採番 |
| 管理情報 | 受付日時 | 日付＋時刻を登録する |
| 管理情報 | 受付方法 | 窓口／電話／メール／要望書／FAX／職員パトロール／その他 から選択。「その他」選択時は自由入力欄に具体的な内容を入力する |
| 管理情報 | 登録者（受付職員） | ログインユーザーと連動想定 |
| 管理情報 | 最終更新日時 | 変更履歴は保持しないが、最終更新日時のみ表示する |
| 相手方情報 | 区分 | 個人／自治会／市町村／議員／匿名／職員パトロール／その他 から選択 |
| 相手方情報 | 要望者 | 氏名・団体名等の自由記述。区分が「匿名」「職員パトロール」の場合は入力不要 |
| 案件情報 | 対応部署 | 道路／河川／砂防 |
| 案件情報 | 要望の内容 | 自由記述 |
| 案件情報 | 種別 | 苦情／要望／異常発見 の区分 |
| 案件情報 | 要望箇所 | 地図上の座標（緯度経度）＋住所表記 |
| 対応情報 | 対応の必要性 | あり／なし／不明 の3種類 |
| 対応情報 | 緊急性 | 高／中／低 の3種類 |
| 対応情報 | 対応方針 | 自由記述 |
| 対応情報 | 対応状況 | 未対応／対応中／対応完了 |
| 対応情報 | 対応完了日 | 対応状況が「対応完了」になった日 |
| 対応履歴 | 対応日 | 実際に対応した日（複数回記録可。「2.6 対応履歴」参照） |
| 対応履歴 | 対応内容 | 対応の経過を自由記述で記録。記録者は訂正後も変更されない |
| 対応履歴 | 記録者 | 記録した職員。ログインユーザーと連動 |

- 現場写真は「2.8 現場写真」で対応する（写真以外の添付ファイルはスコープ外）
- 対応内容・経過記録（対応中の経過を複数回記録する機能）は「2.6 対応履歴」で対応する

### 3.1 ユーザーアカウント項目

「2.5 ユーザー管理・認証」に関連し、ユーザーアカウントとして以下の項目を管理する。

| 分類 | 項目 | 備考 |
|---|---|---|
| アカウント情報 | ユーザーID | ログインに使用。一意 |
| アカウント情報 | 氏名 | |
| アカウント情報 | パスワード | 初期パスワードはシステム管理者が設定し、初回ログイン時に本人が変更する |
| 所属・権限 | 所属事務所 | ログイン時の事務所判定に使用。**一般職員は必須、システム管理者は設定しない**（「1.3 想定利用者・権限方針」参照） |
| 所属・権限 | 担当部署 | 道路／河川／砂防。編集・削除権限の判定に使用。**一般職員のみ設定**（システム管理者は担当部署によらず全案件を編集・削除できるため設定しない） |
| 所属・権限 | 権限区分 | 一般職員／システム管理者 |
| 所属・権限 | アカウント状態 | 有効／無効化（異動・退職時） |

## 4. 非機能要件

### 4.1 セキュリティ・個人情報保護

- 相手方情報は「区分」「要望者」の2項目のみを扱う方針とし、氏名・住所・連絡先・性別・年齢等の詳細な個人情報は原則保持しない
- クローズドな環境での利用（事務所ごとに管理情報を分離し、他事務所の一般職員は閲覧不可）とするため、ID・パスワードによるログイン認証を必須とする
- 編集・削除権限は対応部署（道路／河川／砂防）に応じて制御する（「1.3 想定利用者・権限方針」参照）。ただしシステム管理者は事務所・担当部署によらず全案件を編集・削除できる（個人情報の混入や不適切な記載の是正のため）
- 通信の暗号化（HTTPS）
- 現場写真（2.8）には、通行人の顔・表札・車両のナンバー等、対応に不要な個人情報が写り込まないよう注意を促す（登録フォームに注意書きを表示する）。写り込んだ写真は削除（物理削除）で取り除ける。写真は非公開の保存領域に置き、期限付きの署名付きURLでのみ表示する

### 4.2 可用性・利用環境

- 想定利用場所：インターネット経由でのアクセスを想定
- 想定同時利用者数：最大30人
- 想定データ量：年間最大1,000件程度

### 4.3 保守性・運用

- インフラ方針：本システムは個人開発であり、クラウドはAWSを使用する。既存の別アプリ（famigo）用に手動構築済みのRDSインスタンス（`famigo-mysql`、MySQL、db.t4g.micro）に相乗りし、同一インスタンス内に本システム用のデータベース（スキーマ）を新規作成する形でデプロイし、追加コストを極力抑える方針とする
- バックアップ方針：既存RDSインスタンスの自動バックアップ設定（現状：保持期間1日、バックアップウィンドウ19:32-20:02 UTC）にそのまま従う。本システムのために保持期間の変更（延長）は行わない `[要検討: 保持期間1日で要件上十分か。必要なら延長を検討するが、他システム（famigo）と共用のため変更時は影響範囲を確認する]`
- 復旧目標：RPO（復旧時点目標）24時間、RTO（復旧時間目標）1営業日以内
- データの保存期間：登録から3年間保存し、期間経過後は廃棄する

### 4.4 技術スタック

| 区分 | 技術 |
|---|---|
| バックエンド | PHP / Laravel |
| 画面（テンプレート） | Blade（+ 必要箇所のみ Alpine.js 等で補助） |
| DB | MySQL（既存`famigo-mysql`インスタンスに相乗り。4.3参照） |
| 地図表示 | Leaflet + 国土地理院地図タイル |

**選定理由**

- 本システムはフォーム入力によるCRUD・条件検索・一覧表示・地図上のピン表示が中心の庁内業務システムであり、SPA的なリッチなUIや複雑な状態管理は不要。Laravelはこの種の業務アプリに適したフルスタックMVCフレームワークであり、認証・バリデーション・ORM（Eloquent）・ルーティングが標準機能として揃っている
- 「4.3 保守性・運用」で確定しているEC2 1台への相乗り方針と整合する。Laravel（Blade）は画面表示とAPIを1つのPHPプロセス（PHP-FPM）に統合できるため、EC2上で複数種類の実行プロセス（例：Node.jsとPHPの併存）を管理する必要がなく、構成がシンプルになる
- Eloquent ORMはMySQLを第一級でサポートしており、既存の`famigo-mysql`インスタンスへの相乗り（マイグレーションによるスキーマ管理）と親和性が高い
- 地図表示は要件上ピンの表示・詳細参照・検索結果のフィルタ表示ができれば十分であり、Leafletは軽量かつ無料で導入でき、地図タイルに国土地理院地図（無料・APIキー不要）を用いることで追加コストが発生しない。個人開発としての運用コスト方針（4.3参照）とも整合する
