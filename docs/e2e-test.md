# E2E テスト設計書

本書は、E2E テスト（本物のブラウザで画面を操作する自動テスト）の目的・方法・結果を定義する。
実行手順は [e2e/README.md](../e2e/README.md)、テスト全体の中での位置づけは
[学習用メモ testing-basics.html](learning/testing-basics.html) を参照。

---

## 0. 本書の位置づけ

### 0.1 なぜ行うか

PHPUnit の Feature テストは、「サーバーが正しい HTML を返すか」までしか確かめられない。
画面を開いたあとにブラウザの中で動く JavaScript は、一度も自動で確かめていなかった。

| 画面 | ブラウザの中で動くもの |
|---|---|
| 地図表示 | ピンのデータを取り寄せて、地図上のピンと横の一覧を描く |
| 新規登録・編集 | 地図をクリックすると位置（緯度・経度）が入る。受付方法「その他」で入力欄が出る。対応完了で完了日が入力できる |
| 案件詳細 | 対応履歴の「編集」で表示とフォームが入れ替わる。写真・履歴の削除の確認ダイアログ |
| ユーザー登録・編集 | 権限区分で所属事務所・担当部署の欄が出たり消えたりする |
| 一覧 | 行をクリックすると詳細へ移る |

### 0.2 やらないこと

- **Feature テストで確かめ済みのことは、やり直さない。** 入力チェックの境界値・権限の判定・検索条件の組み合わせなど。
  E2E は1本が重く、落ちたときの原因も探しにくいため、本数は「ブラウザでしか確かめられないこと」と
  「業務の主な流れ」に絞る（4章）。
- **本番には向けない。** テストは案件の登録・削除やユーザーの登録を実際に行う。
- **CI では流さない（今のところ）。** 手元で回す運用から始める（8章）。

## 1. ツール

**Playwright**（Chromium のみ）を使う。選んだ理由は次の3つ。

1. **待ち合わせを自動でしてくれる。** 「ボタンが押せる状態になるまで待つ」「文字が出るまで待つ」を
   Playwright が自動で行う。そのため「何秒待つ」を書かずに済み、不安定になりにくい。
2. **ブラウザの通信を途中で差し替えられる**（`page.route`）。地図タイルをダミー画像にするのに使う（5章）。
3. **失敗したときの記録が見やすい。** 画面の写真と、操作を1手ずつ巻き戻せる記録（トレース）が残る。

ほかの道具を選ばなかった理由は、[学習用メモ](learning/testing-basics.html) 4章を参照。

テストは **TypeScript** で書く。負荷試験（k6）のシナリオは素の JavaScript にしたが、ここは次の理由で変えた。

- Playwright は TypeScript をそのまま実行でき、公式の標準もこちら。ビルドの準備はいらない
- Playwright の機能は多く、型があると書き間違い（存在しない機能名など）に `npm run typecheck` で気づける
- `e2e/` はアプリ本体（Laravel・Vite）から独立したフォルダで、アプリのコードには影響しない

バージョンは公開から2週間以上たったもの（1.64.0）に固定している。公開直後の版に問題があった場合に巻き込まれないため。

## 2. 環境

### 2.1 試験専用の環境

負荷試験（[パフォーマンステスト設計書](performance-test.md) 2章）と同じ考え方で、
**本番と同じイメージ**（`Dockerfile.prod`）を使った試験専用の環境を `docker-compose.e2e.yml` に用意した。
開発用の環境では、画面のキャッシュ・設定のキャッシュなどが本番と違うため、本番に近い形で確かめる。

| | 開発用 | 負荷試験用 | **E2E 用** |
|---|---|---|---|
| compose ファイル | `docker-compose.yml` | `docker-compose.perf.yml` | **`docker-compose.e2e.yml`** |
| プロジェクト名 | （フォルダ名） | `civil-perf` | **`civil-e2e`** |
| ポート | 8081 | 8082 | **8083** |
| DB | `civil_request_management` | `civil_request_perf` | **`civil_request_e2e`** |
| データの置き場所 | ボリューム（残る） | メモリ（止めると消える） | **メモリ（止めると消える）** |

本番との違いは、DB が RDS ではないこと、HTTPS でないこと、写真の保存先が S3 ではなくローカルであること。
写真は保存先こそ違うが、「署名付き URL を発行して、その URL で画像を返す」流れは本番と同じ。

### 2.2 実行スクリプト

`e2e/run-e2e.sh` が「起動 → データ投入 → テスト → 片付け」を1本で行う。
片付けは `trap` で行い、テストの失敗や Ctrl+C でも必ず環境を止めてデータを消す（負荷試験と同じ）。

### 2.3 本番イメージに E2E を入れない

`.dockerignore` に `e2e` を追加した。既存の `node_modules` の行はリポジトリ直下にしか効かず、
`e2e/node_modules` が本番イメージ（`COPY . .`）に入ってしまうため。

## 3. 試験データ

`database/seeders/E2eDataSeeder.php`。テストが「ピンは2本出るはず」のように結果を言い切れるよう、
乱数を使わず、少ない件数を決め打ちで入れる（負荷試験の3,000件とは目的が違う）。

| ユーザーID | 所属 | 使うテスト |
|---|---|---|
| `e2e_road` | みどり土木事務所・道路 | 案件の登録・編集・削除、対応履歴と写真 |
| `e2e_river` | みどり土木事務所・河川 | 他部署の案件は閲覧のみ |
| `e2e_tsubaki` | つばき土木事務所・道路 | 地図 |
| `e2e_admin` | システム管理者 | ユーザー登録 |

| 事務所 | 案件 | 位置 |
|---|---|---|
| みどり | 3件（道路・河川・砂防） | すべてあり |
| つばき | 3件（道路 緊急性「高」、道路 緊急性「低」、河川） | 河川の1件だけ無し → 地図のピンは2本 |
| こはく | 1件 | あり |

- **試験専用 DB の、空の状態でしか動かない**安全装置を付けた。開発用・本番の DB に誤って流しても止まる
  （負荷試験用と同じ。`tests/Feature/E2eDataSeederTest.php` で確認）。
- 文面・住所はすべて架空（CLAUDE.md 6章）。
- テストが案件やユーザーを足すと件数が変わる。そのため、地図のテストはほかのテストが案件を足さない
  つばき土木事務所の職員で行う。

## 4. テスト一覧

| ファイル | テスト | ブラウザでしか確かめられないこと |
|---|---|---|
| `specs/requests.spec.ts` | 案件を登録すると、地図で選んだ位置が詳細画面に出る | 地図クリックで位置が入りピンが立つ、「位置をクリア」、受付方法「その他」の入力欄、一覧の行クリック、詳細の地図のピン |
| 〃 | 編集画面で対応完了にすると完了日が入力でき、削除は確認してから行われる | 完了日の入力可否の切り替え、削除の確認ダイアログ（キャンセル／OK） |
| `specs/request-log.spec.ts` | 写真つきで対応履歴を追加でき、写真の表示・削除ができる | ファイルの選択と送信、**写真が実際に表示できるか**（署名付き URL の画像を読み込めた大きさで確認）、「編集」での表示切り替え、写真削除の確認ダイアログ |
| `specs/map.spec.ts` | 自分の事務所の位置つき案件がピンで出て、ピンから詳細へ進める | ピンと一覧の描画、一覧クリックで吹き出しが開く、吹き出しから詳細へ |
| 〃 | 検索条件で絞り込むと、ピンも絞り込まれる | 画面の検索条件が、JavaScript がピンを取り寄せる通信にも引き継がれる |
| `specs/users.spec.ts` | 管理者が職員を登録し、その職員は初回ログインでパスワードを変えてから使い始める | 権限区分による入力欄の切り替え。ログイン → 強制パスワード変更 → ダッシュボードまでの一連の流れ |
| `specs/permission.spec.ts` | 他部署の案件は閲覧のみで、管理メニューは管理者にしか出ない | （軽い確認）利用者から見て、できない操作のボタンが出ていないか |
| `specs/tiles-external.spec.ts` | 国土地理院の地図タイルが実際に読み込める（`@external`。任意） | 5章 |

### 4.1 書き方の決まり

- **全テストで、画面の JavaScript のエラーを見張る。** エラーが1件でも出たらテストを失敗にする（`fixtures/test.ts`）。
  見た目が正しくても、裏でエラーが出ていれば別の操作が壊れている可能性があるため。
- **テストは1つずつ順に流す**（`workers: 1`）。全テストが同じ DB を使い、登録などでデータが増えるため。
  7本で約30秒なので、同時に流さなくても困らない。
- **失敗しても再実行しない**（`retries: 0`）。再実行で通ってしまうと、「たまに落ちる」不安定さに気づけなくなる。
- **画面の要素は、利用者に見える名前で探す。** ボタン・リンクの文字、ラベルの文字（`getByRole` / `getByLabel`）。
  ラベルが入力欄と結び付いていない項目だけ、入力欄の `name` で探す。
  テスト専用の目印（`data-testid`）はアプリに足さない（アプリのコードをテストの都合で変えないため）。

## 5. 地図タイルの扱い

### 5.1 ふだんはダミー画像に差し替える

地図は、国土地理院のサーバーから256×256ピクセルの小さな画像（タイル）を何十枚も取り寄せて並べている。
E2E テストでは、この取り寄せを Playwright が途中で受け止め、**灰色の無地の画像**を返す（`fixtures/test.ts`）。
地図の背景が灰色になるだけで、ピン・クリック・吹き出しなど**このアプリの JavaScript は本物のまま動く**。

| 確かめたいこと | 背景の画像は関係するか |
|---|---|
| ピンのデータを取り寄せて、正しい位置にピンを出す | しない（ピンは背景とは別の層に描かれる） |
| ピン・一覧のクリックで吹き出しが開き、詳細へ進める | しない |
| 地図をクリックすると、位置が入力欄に入って保存される | しない（位置は Leaflet が計算する） |
| 国土地理院の画像が表示されるか | **する**（ただし国土地理院側の問題） |

本物を読み込むと、国土地理院のサーバーの調子や自宅の回線で、アプリと関係なくテストが落ちることがある。
関係ない理由で落ちるテストは、そのうち「また回線のせい」と無視されるようになり、本当の不具合を見逃す。
また、テストのたびに何十枚も取り寄せるのは、相手のサーバーに不要な負担をかける。

あわせて、地図がタイルを1枚以上要求したこと（地図の部品そのものが動いたこと）は数えて確かめている。

### 5.2 本物を読み込む確認は1本だけ、任意で

残る心配は「国土地理院の URL が変わった」「読み込めなくなった」こと。これは次の2つで備える。

1. `specs/tiles-external.spec.ts`：本物のタイルが1枚返ってくるかだけを確かめる。
   ふだんは流さず、気になったとき（リリース前など）に `E2E_REAL_TILES=1 ./e2e/run-e2e.sh` で流す。
2. 本番へのデプロイ後に、地図が表示されることを画面で見て確かめる（これまでどおり）。

## 6. 結果（2026-10-25）

### 6.1 実行結果

| 実行 | 結果 | 時間 |
|---|---|---|
| ふだんの実行（7本） | すべて成功 | テスト約30秒。スクリプト全体で約50秒（アプリのコードを変えた直後は、イメージの作り直しが入って約3分半） |
| 本物のタイルも含めた実行（8本） | すべて成功 | 約30秒 |
| 同じ環境で7本を3回ずつ繰り返す（`--repeat-each=3`） | 21本すべて成功 | 約1分20秒 |

3回繰り返しても1本も落ちなかったため、「たまに落ちる」不安定なテストは今のところ無い。

### 6.2 わざと壊して、気づけるか確かめた

テストが「通る」だけでなく「壊れたら落ちる」ことを確かめるため、画面の JavaScript を一時的に壊して流した
（確認後に元に戻した）。

| わざと壊したところ | 落ちたテスト |
|---|---|
| 地図をクリックしても緯度が入らないようにした | 案件を登録すると、地図で選んだ位置が詳細画面に出る |
| 権限区分を切り替えても入力欄が消えないようにした | 管理者が職員を登録し、…使い始める |
| ピンのデータを取り寄せる URL を間違えた | 地図の2本とも |

3か所とも、狙ったテストが失敗し、ほかのテストは通った。

## 7. E2E で見つかった不具合

### 7.1 パスワード変更後の完了メッセージが表示されていなかった

パスワードを変更すると「パスワードを変更しました。」と表示されるはずが、実際の画面には一度も出ていなかった。

- 原因：変更後にトップ（`/`）へ転送し、そこからさらにダッシュボードへ転送していた。
  完了メッセージは「次の1回の表示だけ」残る仕組みのため、中継のトップで使い切られていた。
- Feature テストは「トップへ転送されること」までしか見ていなかったため、気づけなかった。
- 対応：ダッシュボードへ直接転送するよう直した（`PasswordController`）。Feature テストにも
  「転送をたどった先の画面にメッセージが出ること」を追加し、直す前のコードでは失敗することを確かめた。

転送の先まで画面として確かめる E2E ならではの発見だった。

## 8. 今後検討

| 項目 | 内容 |
|---|---|
| CI での実行 | 今は手元で回す。PR のたびに流すかは、CI（GitHub Actions）を作るときに改めて決める。流す場合は、本番イメージのビルドと Chromium の準備で数分かかる |
| ほかのブラウザ | Chromium だけで確かめている（テスト時間を短くするため）。要件定義書に対応ブラウザの定めは無いが、役所の PC で多い Edge・Chrome はどちらも Chromium 系。Firefox・Safari での確認が必要になれば追加する |
| スマホの画面幅 | 事務所の PC で使う想定のため、今は対象外（要件定義書に定めは無い） |
| まだ確かめていない JavaScript | ダッシュボード・ユーザー一覧の行クリック、ユーザーの無効化・削除・パスワード再発行の確認ダイアログ。いずれも案件側と同じ書き方のため、優先度は低い |
| CSV 出力 | ファイルのダウンロードは Feature テストで中身まで確かめているため、E2E では扱っていない |
