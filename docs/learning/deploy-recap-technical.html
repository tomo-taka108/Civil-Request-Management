第1幕インフラ構築（Terraform）

AWS に「部屋と通り道」を作る。手作業でなくコードで。

1-1FILETerraform コードを infra/ に作成

目的：「何をAWSに作るか」を10個のファイルに分けて宣言。役割ごとに分割し、既存famigoは参照だけ（data）、新規分だけ作成（resource）と明確に分ける。
ファイル役割要点
versions.tfTerraform本体/プロバイダのバージョン・state保存方式backend "local"＝stateをローカル保存
providers.tfAWS接続設定リージョン東京・全リソースに共通タグ付与
variables.tf値の一覧（famigoの実物ID・ポート・ドメイン）設計書§2の実測ID(VPC/EC2/SG)をdefault化
data.tf既存famigoリソースの参照VPC/ALB/リスナー/EC2/SGを「読むだけ」
target_group.tf振り分け先(TG)＋EC2登録8081・ヘルスチェック/health
security_group.tfEC2 SGに8081許可を1本追加「1ルールだけ」のリソースで既存に触れない
acm.tfHTTPS証明書(DNS検証)ドメイン未設定なら作らない仕掛け
route53.tfDNS(ホストゾーン・レコード)別ゾーン新規作成。famigoに非干渉
listener_rule.tfALB443にホストベースルール追加既定(→famigo)は不変、ルール1本足す
outputs.tf完成後に必要な値の出力ネームサーバー4つ・公開URL等

要点コード（famigo無影響の核）— 既存SGに「1ルールだけ」足す書き方：

infra/security_group.tf 
resource "aws_vpc_security_group_ingress_rule" "ec2_allow_alb_8081" {
  security_group_id            = data.aws_security_group.famigo_ec2.id  # 既存SGに
  referenced_security_group_id = data.aws_security_group.famigo_alb.id  # ALBからのみ
  from_port = 8081
  to_port   = 8081
  ip_protocol = "tcp"
}
# SG本体(aws_security_group)を管理下に置かない＝既存ルールに一切触れない

1-2CMD静的チェック（AWSに触れず・課金なし）

目的：コードの文法・整形が正しいかを、AWSに接続せず確認。
cd infra
terraform init -backend=false   # プロバイダ(AWS操作プラグイン)取得のみ
terraform fmt -recursive        # インデント整形
terraform validate              # 文法・参照の整合チェック → Success

1-3CMDAWS認証（SSO）とドメイン取得

目的：AWSを操作する権限を得る＋利用者の入口(ドメイン)を用意。
aws sso login --profile takashima   # ブラウザでログイン→一時認証(数時間有効)
aws sts get-caller-identity          # 認証できたか確認

お名前.com で civil-track.com を購入（年約1,600円・レンタルサーバー等の抱き合わせは外す）。ネームサーバーは後でRoute53のものに差し替える。

1-4CMDplan（差分プレビュー）→ apply（実作成）

目的：「何が作られるか」を先に確認してから、実際にAWSへ作る。

ドメインの検証は「DNSがRoute53に向いてから」でないと通らないため、2段階で実施した：

# ① まずホストゾーンだけ作る → ネームサーバー4つを取得
terraform apply -target=aws_route53_zone.app -auto-approve
#   出力された ns-xxxx.awsdns-xx... 4つを お名前.com に登録（DNSをRoute53へ向ける）

# ② DNS伝播を確認
nslookup -type=NS civil-track.com 8.8.8.8   # Route53のNSが返ればOK

# ③ 残り全部を作成（ACM証明書・リスナールール・TG・SGルール等）
terraform apply -auto-approve
#   → Plan: 10 to add, 0 to change, 0 to destroy （famigoは0変更・0削除）
💡plan と apply の違い：plan は「作らずに差分を表示するだけ・課金なし」。apply は「実際にAWSへ作る」。毎回 plan で 0 to change / 0 to destroy（＝famigoに触れない）を確認してから apply した。
🔑terraform.tfvars（機密扱い・非コミット）に app_domain_name = "civil-track.com" を書くと、ドメイン依存リソース(ACM/Route53/ルール)が有効化される仕掛けにしてある。

第2幕本番アプリ設定

同じアプリを「本番用の顔」に。これらは事前にコードとして準備済み。

2-1FILEALB越しで正しく動く設定（TrustProxies）

目的：ALBがHTTPSを終端しEC2へHTTPで渡すため、この設定が無いとアプリがHTTPと誤認→cookie不送出・リダイレクトループ。
bootstrap/app.php 
$middleware->trustProxies(at: '*', headers:
    Request::HEADER_X_FORWARDED_FOR
  | Request::HEADER_X_FORWARDED_HOST
  | Request::HEADER_X_FORWARDED_PORT
  | Request::HEADER_X_FORWARDED_PROTO);   # ALBが付ける「元はHTTPS」の印を信頼

2-2FILE本番用の環境設定ファイル

目的：ローカル用(APP_DEBUG=true等)を本番に持ち込まない。本番専用の雛形を分離。
.env.production.example（抜粋） 
APP_ENV=production
APP_DEBUG=false          # 必須：例外画面に内部情報を出さない
APP_URL=https://civil-track.com
DB_HOST=famigo-mysql....rds.amazonaws.com
DB_DATABASE=civil_request_management   # 本システム専用スキーマ
SESSION_SECURE_COOKIE=true       # HTTPSでのみcookie送信
# APP_KEY / DB_PASSWORD は空 → 本番で実値を入れる（機密はコミットしない）

2-3FILE本番用の起動イメージ・手順

目的：本番はソースをイメージに焼き込み、起動時にDB更新＆高速化を自動実行。
ファイル役割・要点
docker/php/Dockerfile.prodPHP実行環境。composer install --no-devで本番依存のみ＋ソース焼き込み
docker/nginx/Dockerfile.prodNginx。public/を焼き込み静的配信、PHPへfastcgi
docker/php/entrypoint.prod.sh起動時にmigrate --force＋config/route/view:cache
docker-compose.prod.ymlNginx+PHPの2コンテナ。famigoと完全分離（専用network/8081公開）
docker/php/entrypoint.prod.sh（要点） 
php artisan migrate --force   # DBテーブルを最新に（対話プロンプト無し）
php artisan config:cache      # 設定を事前キャッシュ＝高速化
php artisan route:cache
php artisan view:cache

第3幕デプロイ作業

用意した部屋に、本番仕様のアプリを実際に設置して動かす。

🖥️ この幕の作業は「誰が・どう実行したか」

本来この一連（EC2にフォルダを作る→コードを取り込む→RDSに入ってDB・テーブル・初期データを作る→Dockerをビルド・起動）は、EC2 のターミナルに入って手でコマンドを打つ作業。今回は AI（私）が SSM Run Command 経由でコマンドを送り込み、利用者の代わりに実行した（aws ssm send-command ...）。手でログインして打つのと結果は同じ。

ただし機密が絡む箇所だけは利用者が手打ち：RDS の CREATE DATABASE/USER/GRANT（マスターパスワードをログに残さないため）と、.env.production への APP_KEY・DBパスワード記入。これらは AI のコマンド履歴に残さないよう、利用者の手元セッションで実施した。

♻️ これらは基本「一度きり」の構築作業。作ったフォルダ・コード・Swap・RDSのDB/テーブル/初期データは、EC2/RDSを停止しても消えず残るため、次回以降やり直す必要はない。毎回必要なのはコンテナ起動だけで、それも restart: unless-stopped で自動復帰する見込み。詳細は末尾の「再実行が必要か早見表」を参照。

3-1CMDEC2に入る手段＝SSM で環境調査

目的：鍵不要でEC2を遠隔操作。まず中身(docker/git等)を調べる。
# EC2に「コマンドを送って結果を受け取る」方式（対話ログイン不要）
aws ssm send-command --instance-ids i-0dcf0d521ec4ae906 \
  --document-name "AWS-RunShellScript" \
  --parameters 'commands=["docker --version; git --version; free -h"]'
# 判明：docker有／git無し／メモリ実質1GB弱でSwap 0

3-2対処CMDメモリ保険：Swap 2GB追加

目的：メモリ不足でアプリが強制終了しfamigoが巻き添えで落ちるのを防ぐ避難場所を用意。
fallocate -l 2G /swapfile; chmod 600 /swapfile
mkswap /swapfile; swapon /swapfile
echo "/swapfile none swap sw 0 0" >> /etc/fstab   # 再起動後も有効

3-3CMDアプリのコードをEC2に配置

目的：動かす実体を運び込む。gitが無いのでtarball(zip)を取得して展開。
mkdir -p /opt/civil && cd /opt/civil
curl -fsSL -o main.tar.gz \
  https://github.com/tomo-taka108/Civil-Request-Management/archive/refs/heads/main.tar.gz
tar xzf main.tar.gz --strip-components=1   # /opt/civil に展開
# 続いて .env.production を作成（APP_KEY生成・DB_PASSWORD等を記入）

3-4CMDRDSに専用スキーマ・ユーザー・テーブルを作成

目的：データ保存先を用意。famigoと棚を分け、専用ユーザーは自分の棚しか触れない最小権限。

マスター権限のSQLは機密のためログに残さず手元(EC2セッション)で実行：

-- RDSにマスターユーザーで接続して実行
CREATE DATABASE civil_request_management CHARACTER SET utf8mb4 COLLATE utf8mb4_ja_0900_as_cs;
CREATE USER 'civil_request_app'@'%' IDENTIFIED BY '(生成したパスワード)';
GRANT SELECT,INSERT,UPDATE,DELETE,CREATE,ALTER,INDEX,DROP,REFERENCES
  ON civil_request_management.* TO 'civil_request_app'@'%';
# テーブル生成と初期データ投入（コンテナ経由でartisan実行）
docker compose -f docker-compose.prod.yml run --rm --no-deps php php artisan migrate --force
... db:seed --class=OfficeSeeder --force      # 事務所3件
... db:seed --class=AdminUserSeeder --force   # 管理者admin

3-5対処本番特有のつまずきを解消

目的：ローカルと違う本番環境で、実際に動かして判明した差異を1つずつ潰す。
症状原因対処
ビルドがbuildx 0.17必要で失敗EC2のbuildxが旧版(0.12)DOCKER_BUILDKIT=0で旧ビルダー使用
外部キー作成でREFERENCES denied専用ユーザーにREFERENCES権限なしマスターでGRANT REFERENCES追加
users already existsが消えない再起動ループ中のコンテナが裏でmigrate実行しDBを汚染compose downで停止→DROP→migrateやり直し
git無しfamigoは事前ビルドjar方式tarball取得に切替(3-3)

3-6CMDコンテナ起動＆開通確認

目的：「ブラウザ→ALB→EC2→RDS」が実際に一本つながったか最終確認。
# ビルド→起動
export DOCKER_BUILDKIT=0 COMPOSE_DOCKER_CLI_BUILD=0
docker compose -f docker-compose.prod.yml build
docker compose -f docker-compose.prod.yml up -d

# 確認①：EC2内でヘルスチェック
curl -s -o /dev/null -w "%{http_code}" http://localhost:8081/health   # → 200
free -h                                                          # メモリ実測（famigo無事）

# 確認②：ALBのターゲットが healthy か
aws elbv2 describe-target-health --target-group-arn ...          # → healthy

# 確認③：インターネット経由（HTTPS）
curl https://civil-track.com/health                              # → 200
curl -I https://civil-track.com/                                 # → 302 /login（ログイン画面へ）

早見表この作業、次回も要る？

第3幕でやった各作業が「一度きり（完了済み）」か「起動のたびに必要」か。停止→再開のたびにゼロからやり直す必要はない。

作業種別次回以降
EC2 /opt/civil フォルダ作成一度きり✅ 不要（ディスクに残る）
コード配置（tarball展開）一度きり✅ 不要 ※コード更新時のみ再取得
Swap 2GB 追加一度きり✅ 不要（fstab登録で再起動後も有効）
.env.production 作成一度きり✅ 不要（設定変更時のみ編集）
RDS の DB・ユーザー・GRANT 作成一度きり✅ 不要（RDSに永続。停止しても消えない）
テーブル生成（migrate）・初期データ（seed）一度きり✅ 不要 ※スキーマ変更時のみ追加migrate
Terraform インフラ（ALB/証明書/DNS等）一度きり✅ 不要（AWSに存在し続ける）
Dockerコンテナの起動（up -d）起動のたび🔁 EC2再開時に必要。ただし restart: unless-stopped で自動復帰する見込み。出なければ手動 up -d 1回
📌まとめ：停止→再開で戻るのは「コンテナ起動」だけ。フォルダ作成やDB作成に戻る必要は無い。コードを更新したい時だけ「コード再取得＋ビルド＆起動」を行う（DB作成等は不要）。再開手順の詳細は docs/operations-start-stop.md。
