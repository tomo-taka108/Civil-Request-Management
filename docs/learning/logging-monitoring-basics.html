1何のためのログ・監視か

ひとことで：ログは「あとで調べるための記録」、監視は「異常にすぐ気づくための仕組み」。

本番のアプリは、開発中と違って画面の裏で何が起きているかが見えません。利用者から「さっきエラーが出た」と言われても、記録が無ければ推測するしかありません。障害や問い合わせのときに知りたいことは、突き詰めると次の3つです。

知りたいこと答えるための情報
何が起きたかエラーの内容・どの処理か（メッセージ、スタックトレース）
誰に起きたかユーザーID
いつ・どの操作の中で時刻、リクエストID（1回の操作に関わるログ行を束ねる番号）

ただしログは、誰かが見に行かない限り何も教えてくれません。夜中にサイトが落ちていても、ログに書かれているだけでは翌朝まで気づけません。そこで「おかしくなったら知らせる」役割を持つのが監視です。

たとえ：ログは飛行機のフライトレコーダー（事故のあとで原因を調べる）。監視はコックピットの警告ランプ（異常をその場で知らせる）。どちらか片方では足りません。

2ログ・メトリクス・アラーム

似ているけれど役割が違う3つ。監視は「メトリクス」と「アラーム」の組み合わせで動く。

ログ

1つ1つの出来事の記録

「10:03 に staff101 がログインした」「10:05 に写真の保存で失敗した」のように、1行＝1つの出来事。詳しいが量が多い。

たとえ：日記

メトリクス

数値の移り変わり

「ディスク使用率 78%」「5分間のエラー件数 0件」のように、数値を時間ごとに記録したもの。グラフにでき、しきい値と比べやすい。

たとえ：体温計の記録

アラーム

しきい値を超えたら知らせる

「メトリクスが○○を超えたら、メールで知らせる」というルール。人が見ていなくても気づけるようになる。

たとえ：「38度を超えたら連絡」という約束

ログからメトリクスを作ることもできます。たとえば「ERROR と書かれたログ行の数を5分ごとに数える」と、それはエラー件数というメトリクスになり、アラームを付けられます。この「ログ → 数える → アラーム」がこのアプリの監視の中心です（8章）。

📌もう1つ「トレース」という柱もあります（1つの処理が複数のサービスをまたいでどう流れたかの記録）。このアプリは1つのサーバーで完結する作りなので、今回は扱いません（SnsTimeLineApp と同じ判断）。

3ログレベルの使い分け

「どれくらい重要な出来事か」を表すラベル。設定したレベル以上だけが出力される。

レベル判断基準このアプリでの例
ERROR人が対応すべき異常。アプリの外側（インフラ）やバグが原因写真を S3 に保存できなかった／想定外の例外（500 エラー）
WARNING想定内だが、記録しておきたい失敗ログイン失敗（パスワード違い）
INFO正常な業務上の出来事ログイン成功、案件の削除、写真の保存、1リクエスト1行のアクセスログ
DEBUG開発中の調査用。本番では出さないSQL の中身など

迷いやすい境界

  • 「ログイン失敗」は WARNING、「S3 への保存失敗」は ERROR。前者は利用者の入力ミスという想定内の出来事。後者はサーバー側の異常で、人が気づいて対応する必要がある。「利用者が原因か、サーバー側が原因か」が境目。
  • 入力チェックのエラー（必須項目の未入力など）はログに出さない。画面で利用者に伝えれば済み、記録しても調査の役に立たないため。
  • 本番は INFO 以上を出す。今の本番は WARNING 以上しか出ない設定のため、正常な操作の記録が一切残っていない。

4構造化ログ（JSON）

ひとことで：人が読む文章ではなく、機械が項目ごとに検索できる形で書く。

Laravel の既定のログは、人が読むための1行の文章です。

[2026-10-20 10:05:12] production.ERROR: 写真の保存に失敗しました {"request_id":"8cce…"}

人が読む分には困りませんが、「ERROR だけ」「ユーザー 12 のものだけ」と絞り込もうとすると、文字列の中を探すしかありません。そこで、1行を JSON（項目名と値の組）で出します。

// 実際は1行。読みやすいよう改行している（ローカルで本番と同じ設定にして採取）
{
  "message": "写真の保存に失敗しました",
  "context": { "case_id": 12, "disk": "s3" },      ← この出来事に固有の値
  "level_name": "ERROR",
  "datetime": "2026-10-20T10:05:12+09:00",
  "extra": { "request_id": "8cce8924-…", "user_id": 5 }  ← 全行に自動で付く
}

こうしておくと、CloudWatch で { $.level_name = "ERROR" } のように項目を指定して検索・集計できます。エラー件数を数えてアラームにする（8章）のも、この形だからできることです。

💡ローカル開発では従来の文章形式のままにします。開発中に JSON が流れると人には読みにくいためです。本番だけ JSON にするのは SnsTimeLineApp と同じ考え方です。

5リクエストID

ひとことで：1回の画面操作に番号を振り、その操作中に出たログ行すべてに同じ番号を付ける。

本番では、複数の利用者の操作が同時に進み、ログ行が混ざって流れてきます。「さっきのエラーの直前に何をしていたか」を追うには、同じ操作のログ行を束ねる印が必要です。それがリクエストIDです。

① 受け付けリクエストが届いたら番号を決める（例 8cce…）
→
② 処理中この間に出るログ行に、番号とユーザーIDを自動で付ける
→
③ 返すレスポンスにも同じ番号を付ける（エラー画面に表示）

エラー画面に番号を表示しておけば、利用者から「この番号のエラーが出ました」と聞くだけで、その操作のログが一発で揃います。

外から来た番号は、そのまま信用しない

リクエストIDは、外部（ロードバランサや別のシステム）から X-Request-Id ヘッダで渡されることもあります。ただし、悪意のある人が改行を含む値を送ると、ログに偽の行を書き込まれるおそれがあります（ログインジェクション）。そのため、英数字とハイフンだけ・64文字以内の値だけを受け入れ、それ以外は自分で番号を振り直します。

6ログに出してはいけないもの

ログは、アプリの画面より多くの人・場所に渡る。だから「念のため全部出す」は危ない。

出さないもの理由
パスワードログを見られる人すべてに漏れる。ログイン失敗時に入力値を出すのも厳禁
要望者の名前・要望内容このアプリが扱う個人に関わる情報（CLAUDE.md 6章）。案件はIDだけで記録する
検索の語句（URL のクエリ文字列）一覧の検索欄に要望者名を入れると、URL の ?keyword=… に載る。アクセスログはパスだけを記録する
写真のファイル名利用者が名前や住所を含むファイル名を付けることがある
署名付きURL・セッション・Cookieそれ自体が「鍵」。漏れると他人がその写真やログイン状態を使える
DB エラーに含まれる値Laravel の既定では、DB エラーのメッセージに SQL と埋め込まれた値（要望者名など）がそのまま入る。DB エラーだけは独自に記録し、値を ? のままにする（実装で気づいた落とし穴）

これらは「気をつける」だけでは守りきれません。そこで、テスト用のパスワードや要望者名で操作してから、出たログを全行調べ、1行も含まれていないことを自動テストで確かめます（SnsTimeLineApp の #474 と同じ方式）。

テストが本当に見張れているかも確かめました。わざと守りを外す（DB エラーの独自記録をやめる、アクセスログにクエリ文字列を付ける）と、テストが3件失敗します。

7Docker のログはどこへ行くか

ひとことで：コンテナが画面（標準出力）に書いたものを、Docker が「ログドライバ」で決まった場所へ運ぶ。

その前に：ログは nginx と Laravel の2種類ある

このアプリは、リクエストを2つのプログラムで順番に処理しています。それぞれが自分の見たことを記録するので、ログも自然と2種類になります。

ブラウザ→ ALB
→
nginx（受付係）全部のリクエストを受け取る。CSS・画像は自分で返し、それ以外を PHP へ回す
→
Laravel（担当者）ログイン判定・案件の検索や登録など、業務の処理をする
nginx のログ（来客記録）Laravel のログ（業務日誌）
記録する範囲全部のリクエスト（CSS・画像も）PHP に回ってきたものだけ
誰の操作か分からない分かる（user_id）
何をしたかURL と結果の番号（200・404・500 など）だけ業務の意味まで分かる（「写真を2枚保存した」）
エラーの中身「500 だった」までどこで何の例外が起きたかまで
PHP が止まったとき記録できる（502 を返した記録が残る）記録できない（自分が動いていない）

両方あると切り分けができます。「エラーが出た」なら Laravel のログで原因まで追えます。「画面が真っ白」で Laravel のログに何も無ければ、nginx のログの 502 から「PHP が止まっている」と分かります。「デザインが崩れた」なら、CSS は nginx が直接返すので nginx のログを見ます。

今回は2つを同じ考え方で揃えました。どちらも JSON 1行で、検索語（クエリ文字列）は残しません。さらに nginx 側にも Laravel が付けたリクエストIDを記録するので、同じ番号で検索すれば来客記録と業務日誌の該当箇所が一緒に出てきます。

Docker がログを運ぶ仕組み

コンテナの中のプログラムは、ログを標準出力（stdout）・標準エラー出力（stderr）に書くのが基本です。それを受け取った Docker が、ログドライバの設定に従って保存先へ運びます。

コンテナnginx・PHP がログを stdout / stderr に書く
→
Dockerログドライバが受け取る
→
json-file（既定・今の本番）EC2 のディスクにファイルとして溜まる
awslogs（今回の変更後）CloudWatch Logs へ送る。ディスクに溜まらない

今の本番の問題

  • Laravel のログはコンテナ内のファイル（storage/logs/laravel.log）に書かれている。保存場所がコンテナの中なので、デプロイで作り直すと消える。見るにはコンテナに入る必要もある。
  • nginx のログは既定のログドライバ（json-file）で EC2 のディスクに書かれ、上限なしで増え続ける。famigo と共用の 8GB のディスクを少しずつ圧迫する（Issue #102）。

そこで、Laravel も stderr に出すように変え、ログドライバを awslogs にして CloudWatch へ送ります。こうすると、EC2 のディスクにログが溜まらず、作り直しても消えず、ブラウザから検索できるようになります。

⚠️順番に注意。awslogs ドライバは、送り先（ロググループ）と送る権限（IAM）が無いとコンテナが起動しません。AWS 側の準備 → デプロイ、の順で進めます。

メモ：ログが CloudWatch に届くまで（「Docker が送る」のに「EC2 で認証」？）

混乱しやすい点は、EC2・Docker・コンテナが入れ子になっていることです。EC2 の中で Docker 本体が動き、Docker の中でコンテナが動いています。

┌─ EC2（1台のパソコン・famigo と共用）── 社員証：IAM ロール famigo-EC2-SSM-Role ─┐
│  ┌─ Docker 本体（EC2 の上で動く管理プログラム）────────────────┐  │
│  │   [nginx コンテナ]   [php コンテナ]   [famigo コンテナ]          │  │
│  └─────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────┘

だから「Docker が送る」と「EC2 の権限で認証する」は矛盾しません。EC2 の中にいる Docker が、EC2 の社員証を借りて送っている、という1つの出来事です。

順どこで何が起きるか
①コンテナの中Laravel は stderr に、nginx は stdout に JSON を1行書く。ファイルには保存しない（「声に出して言っただけ」）
②Docker 本体コンテナの画面出力をすべて受け取る。ログドライバ（受け取ったログをどうするかの設定）が awslogs なので、CloudWatch へ送る。設定場所は docker-compose.prod.yml の logging:
③Docker 本体 → AWSCloudWatch に「誰が書くのか」を示すため、EC2 の社員証（IAM ロール）を見せる。社員証は EC2 から自動で受け取れるので、キーやパスワードは置かない。社員証に書き足した許可が CivilTrackLogsAndMetrics
④CloudWatch Logsロググループ /civil/app（本システム専用の書庫）の中の、ログストリーム php・nginx（送り元ごとの棚）に保管される
⑤CloudWatch → あなたERROR の行を数える → アラーム → SNS → メール
キーワードひとことでどこにあるか
stderr / stdoutコンテナの「画面出力」各コンテナの中
ログドライバ（awslogs）Docker が「ログをどこへ運ぶか」の設定docker-compose.prod.yml の logging:
IAM ロールEC2 の社員証EC2 に付いている（AWS 側）
インラインポリシー社員証に書き足した「/civil/app にログを書いてよい」の許可infra/monitoring.tf
ロググループ／ログストリームCloudWatch 上の専用の書庫／その中の棚infra/monitoring.tf（ストリームは Docker が自動で作る）

まとめ：書くのはコンテナ、運ぶのは Docker、運ぶときに見せる許可証は EC2 のもの、保管するのは CloudWatch。

8CloudWatch の部品

AWS の監視サービス。ログの保管・数値化・アラーム・通知を組み合わせて使う。

CloudWatch Logsログを保管・検索
→
メトリクスフィルタ条件に合う行を数えて数値にする
→
アラームしきい値を超えたら発動
→
SNSメールで通知

CloudWatch Logs（ロググループ・ログストリーム）

役割：ログの保管庫。ブラウザから検索できる

ロググループはアプリ単位の大きな箱（このアプリは /civil/app）。その中に、送り元ごとのログストリーム（nginx 用・PHP 用）ができる。ロググループには保持期間を設定でき、古いログは自動で消える（今回は30日の予定）。

たとえ：書庫（ロググループ）と、その中の棚（ログストリーム）。保存期限を過ぎた書類は自動で廃棄される。

メトリクスフィルタ

役割：ログの中から条件に合う行を数え、メトリクスにする

たとえば「level_name が ERROR の行」を数えて「エラー件数」というメトリクスを作る。4章の JSON 形式だから、項目を指定して正確に数えられる。

アラーム

役割：メトリクスを見張り、しきい値を超えたら動く

「5分間のエラー件数が1件以上」のような条件を決める。状態は OK（正常）／ALARM（異常）／データ不足の3つで、OK → ALARM に変わった瞬間に通知が飛ぶ。

SNS（Simple Notification Service）

役割：通知の配達係

アラームから「異常です」と受け取り、登録したメールアドレスへ送る。登録時に確認メールが届き、リンクを押すと受信が始まる。

料金の目安

AWS の無料枠には2種類あります。「12か月無料」（EC2・RDS など。アカウント作成から1年で終わる）と、「常に無料（Always Free）」（期限なし）です。CloudWatch と SNS の下の枠は常に無料のほうなので、12か月の無料期間が終わったアカウントでも毎月使えます。

アラーム見張るもの発動する条件
① エラー発生ログ中の ERROR 行の数（メトリクスフィルタ）5分間に1件以上
② サイト停止ALB が「正常」と判定しているサーバーの数1台未満が続いたとき
③ ディスク逼迫EC2 のディスク使用率（5分ごとに送る）85% 以上
  • ディスク使用率は AWS が自動では集めてくれない数値のため、EC2 上で5分ごとに df の結果を CloudWatch に送る小さな仕組みを置く（常駐プロセスを増やさないよう、専用のエージェントは入れない）。
  • EC2 を止めている間は②が「異常」になる。止めたときにメールが1通届くのは仕様として扱う。
  • famigo の既存の設定は変えず、本システム用の権限（インラインポリシー）を追加するだけにする。

なぜ Datadog ではなく CloudWatch か

観点DatadogCloudWatch
費用サーバー監視・ログ管理は有料（サーバー1台あたり月数千円〜）。無料プランはログ管理やアラートの機能が限られる常に無料の枠内で0円の見込み
EC2 への負担専用のエージェント（常駐プログラム）を入れる必要があり、メモリを数百MB使うDocker の機能（awslogs）で直接送れる。常駐プログラム不要
famigo への影響共用の t3.micro（空きメモリ約280MB）では、famigo を巻き込んでメモリ不足になるおそれ影響なし
鍵の管理Datadog の API キーをサーバーに置いて管理するEC2 の IAM ロールで認証（S3 と同じ仕組み）。鍵を置かない
得意なこと画面が見やすい、複数のクラウドをまとめて見られる、性能分析（APM）が強いAWS の中で完結する構成に向く。機能は素朴

このアプリは AWS だけで動く小さな構成で、しかも famigo と共用の小さなサーバーに載っています。費用・サーバーへの負担・鍵の管理の3点で CloudWatch が合うと判断しました。なお SnsTimeLineApp でも「アプリは標準出力に出すだけにしておけば、Datadog でも CloudWatch でもアプリ側は変えずに済む」という設計にしていました。今回の作りも同じなので、将来 Datadog に乗り換える場合もアプリのコードは変わりません。

10障害時の調べ方 予定

アラームのメールが届いた、または利用者から問い合わせがあったときの流れ。

利用者から「エラーが出た」と言われたら

  1. エラー画面に表示されたリクエストIDを聞く（無ければ、おおよその時刻と操作）
  2. CloudWatch Logs で、そのリクエストIDを検索する → その操作のログ行がすべて揃う
  3. 同じユーザーIDで前後の操作を見て、何をしようとしていたかを確かめる
  4. ERROR 行のメッセージとスタックトレースから原因を探す

アラームのメールが届いたら

アラームまず見るところよくある原因と一次対応
① エラー発生CloudWatch Logs で ERROR 行を検索S3 の権限・一時的な通信エラー、バグ。再現手順が分かれば Issue 化
② サイト停止ブラウザで /health、EC2 の状態、docker psEC2 を停止している（想定内）／コンテナが落ちている → 再起動
③ ディスク逼迫EC2 で df -h /、docker system df古いイメージの蓄積 → docker image prune -a。続くなら EBS 拡張（#102）
