CI · 基礎と導入

CI の基礎 ── 仕組み・使う技術・このアプリでの作り方

CI（継続的インテグレーション）は「コードを GitHub に送るたびに、決まったチェックをロボットが自動でやってくれる仕組み」です。何のためにあり、どこで・いつ・何が動くのか。基礎を整理したうえで、このアプリに GitHub Actions で CI を入れたときの考え方と、設定ファイル（.github/workflows/ci.yml）の読み方をまとめます。

1CI とは

ひとことで：手で回している品質チェックを、GitHub 側で毎回・自動で・必ず回す仕組み。

このアプリでは、コミットの前に Pint（書式）・PHPStan（静的解析）・PHPUnit（自動テスト） の3つを手で回すルールにしています（quality-check）。CI は、これと同じことを PR を出すたびに GitHub が自動でやってくれるようにするものです。

CI = Continuous Integration（継続的インテグレーション）

「インテグレーション（統合）」は、自分の変更を main に合流させること。「継続的」は、それを小さく・何度も行うこと。合流させる前に、毎回自動でチェックを通すのが CI の中心です。

たとえ：空港の保安検査。乗客（変更）は全員、毎回、同じ機械を通る。「自分は大丈夫」と思っていても通る。人の記憶や気分に頼らず、決まった確認を必ず通すことで安全を保ちます。

2何のためにあるか

ひとことで：やり忘れを防ぎ、「自分の PC でだけ動いた」を見つけ、合否を一目で分かるようにする。

① やり忘れを防ぐ

手で回すルールは、急いでいるときや「小さな直しだから」と思ったときに抜けます。CI は毎回必ず回るので、抜けがありません。

② 「自分の PC では動いた」を見つける

CI は GitHub にあるファイルだけで、新品のコンピューターに一から組み立てて試します。手元にだけあるファイルや設定に頼って「たまたま通った」状態を見つけられます（7章）。

③ 合否が PR 画面で一目で分かる

PR に ✅／❌ が付くので、マージしてよいかをすぐ判断できます。「テストは通しましたか？」と聞く必要がなくなります。

④ main を「いつでも動く状態」に保つ

❌ の変更を main に入れない、というルールを GitHub の設定で強制できます（ブランチ保護。10章）。main から取ったコードは常にチェック済み、という安心につながります。

3CI と CD の違い

ひとことで：CI は「確かめる」まで、CD は「本番に届ける」まで。このアプリは CI だけを作る。

CI変更のたびに自動でチェックする
→
継続的デリバリーいつでも本番に出せる形（イメージ等）まで自動で作る。出すボタンは人が押す
→
継続的デプロイマージしたら本番まで自動で反映する

後ろの2つをまとめて CD と呼びます。このアプリでは CI だけを作り、CD は作りません。

CD を作らない理由中身
famigo と同じ EC2 に相乗りfamigo を止めないことが最優先。今の手順には「famigo-api が動いているのを確かめてから古いイメージを消す」など、人が目で見て判断する場面がある
ディスクに余裕がない普段 78%、ビルド中は 82〜83%。自動で回すと、気づかないうちにいっぱいになるおそれがある（#102）
AWS の権限を GitHub に渡すことになる「本番 AWS の変更は人が手で打つ」方針に反する。渡すなら権限の設計から必要
デプロイは月に数回自動化で減る手間が小さく、作る手間とリスクに見合わない
🧭将来やるなら。GitHub が AWS に一時的にだけ入れる仕組み（OIDC）を使い、イメージは CI で作って AWS の保管場所（ECR）に置き、EC2 は受け取るだけにする形が考えられます。EC2 でビルドしなくなるのでディスクの問題も軽くなります。今は設計書の「今後検討」に残しています。

4仕組み：どこで動くのか

ひとことで：あなたの PC ではなく、GitHub が貸してくれる使い捨てのコンピューターで動く。

💻 あなたの PC

  1. コードを編集してコミット
  2. git push ／ gh pr create
  3. （あとは待つだけ。PC の電源を切っても CI は続く）
  4. PR 画面で ✅／❌ を見る

☁️ GitHub（インターネットの向こう）

  1. PR が来たことに気づく
  2. 使い捨ての Linux のコンピューター（ランナー）を1台起動
  3. GitHub にあるコードだけを取ってくる
  4. PHP・MySQL を用意し、3つのチェックを実行
  5. 結果を PR に書き込み、コンピューターは捨てる

大事なのは、ランナーには「push されたもの」しか無いことです。あなたの PC にあって GitHub に無いファイル（コミットし忘れたファイル、.env、手元のDBに残ったデータなど）は存在しません。毎回まっさらな状態から始まるので、前回の実行の残りカスにも左右されません。

ローカルの quality-checkCI
どこであなたの PC（Docker のコンテナ）GitHub のランナー（毎回新品）
いつコミット前に手でPR を作った・更新したとき、main にマージしたとき（自動）
使うコード手元のファイル全部（未コミットも含む）GitHub に push されたものだけ
役割早く気づいて、すぐ直す最後の関所。新品の環境で「本当に大丈夫か」を確かめる

CI を入れてもローカルのチェックはやめません。手元で先に見つけるほうが早く直せるからです。CI は抜けを拾う安全網です。

5使う技術（GitHub Actions の部品）

ひとことで：「いつ（トリガー）」「どこで（ランナー）」「何を（ジョブ・ステップ）」を YAML ファイル1枚に書く。

GitHub Actions は GitHub に組み込まれた自動実行の仕組みです。リポジトリの .github/workflows/ に YAML ファイルを置くだけで動きます。公開リポジトリなら無料で使えます（このリポジトリは公開なので 0 円）。

部品役割ci.yml での書き方
ワークフロー自動実行の手順書1枚。YAML ファイル1つが1ワークフロー.github/workflows/ci.yml、name: CI
トリガーいつ動かすかon: の pull_request・push・workflow_dispatch
ジョブ1台のランナーで行う作業のまとまり。複数あれば並行して走らせられるjobs: の quality（今回は1つ）
ランナージョブを実行する使い捨てのコンピューターruns-on: ubuntu-24.04
ステップジョブの中の1つ1つの作業。上から順に実行steps: の各 - name:
アクション誰かが作って公開している「よく使う作業の部品」uses: actions/checkout@… など
サービスコンテナジョブの横で一緒に動かすコンテナ。DB などに使うservices: mysql:
キャッシュ前回ダウンロードしたものを次回に使い回して速くするactions/cache
権限ワークフローがリポジトリに対してできることpermissions: contents: read
同時実行の制御同じ PR の古い実行を止めるconcurrency:

ランナーの上で使うもの

道具役割
actions/checkoutGitHub からコードを取ってくる（git clone にあたる）
shivammathur/setup-php指定した版の PHP と拡張機能・composer を入れる。Laravel の CI で広く使われている
MySQL 8.4（サービスコンテナ）テスト用の DB。開発環境の docker-compose.yml と同じイメージ

6いつ動くか（作業の流れに当てはめる）

ひとことで：PR を作った瞬間から、その PR に push するたびに動く。マージ後にもう一度動く。

「main 向けの PR」は、マージ先（base）が main の PR のことです。gh pr create --base main で作る PR はすべて当てはまります。

  • ブランチを作って編集・コミット動かない
  • git push（まだ PR は無い）動かない
  • gh pr create（main 向けの PR を作る）動く
    PR 画面に「チェック中」→ ✅／❌
  • 直しをコミットして同じブランチに pushもう一度動く
    前の実行がまだ途中なら、それは止めて新しいほうだけ回す
  • あなたが PR をマージmain で最後にもう一度動く
    PR を同時に複数出したときなど、組み合わせで壊れていないかの確認

このほか、GitHub の「Actions」タブからボタンで手動実行もできます（workflow_dispatch）。

7CI が見つけられること・られないこと

ひとことで：「必要な部品が足りない」「テストに書いたことが壊れた」は見つかる。「書いていないこと」は見つからない。

見つかる例：マイグレーションの入れ忘れ

案件テーブルに「優先度（priority）」の列を足したのに、マイグレーションのファイルだけ git add し忘れた場合です。

ファイルコミットに入ったか
マイグレーション（priority 列を足す）入れ忘れ
モデル・コントローラー（priority を使う）入っている
テスト（priority を保存できるか確かめる）入っている
// あなたの PC：マイグレーションのファイルが手元にあるので、priority 列ができる
Tests: 207 passed  ✅

// CI：GitHub にファイルが無いので、priority 列が作られない
SQLSTATE[42S22]: Column not found: 1054 Unknown column 'priority'
Tests: 1 failed, 206 passed  ❌

CI は「GitHub にあるものだけ」で一から組み立てるので、コミットしたコードが必要とする部品が足りないと、そこで止まります。新しく作ったクラスのファイルを入れ忘れた場合も、PHPStan とテストが「クラスが見つからない」と ❌ になります。

見つからない例

  • テストファイルだけの入れ忘れ：GitHub に無いテストは「存在しない」扱いで、実行されないので ✅ になる。
  • テストを書いていない動き：CI はテストに書いたことしか確かめない。画面の見た目や、テストの無い機能の不具合は見つからない。
  • 本番でしか起きないこと：本番の設定・S3・ALB などは CI では使わない。
💡一番の予防はコミット前の git status。新しく作ったファイル（Untracked files）が残っていないかを見る習慣が先で、CI はその見落としを拾う安全網です。

8このアプリの ci.yml を読む

ひとことで：「PHP と MySQL を用意 → パッケージを入れる → .env を作る → 3つのチェック」。

① いつ・どんな権限で動くか

on:
  pull_request:          # main 向けの PR を作った・更新したとき
    branches: [main]
  push:                  # main にマージされたとき
    branches: [main]
  workflow_dispatch:     # 画面のボタンで手動実行

permissions:
  contents: read        # コードを読むだけ。書き込みはさせない

concurrency:            # 同じ PR の古い実行は止める
  group: ci-${{ github.ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}

② テスト用の MySQL を横で動かす

services:
  mysql:
    image: mysql:8.4                       # 開発環境と同じ版
    env:
      MYSQL_DATABASE: civil_request_management_testing  # phpunit.xml と同じ DB 名
      MYSQL_USER: civil_request_app
      MYSQL_PASSWORD: ci_password           # CI 専用の使い捨ての値
    options: --health-cmd="mysqladmin ping -h 127.0.0.1 ..."  # 起動完了まで待つ

開発環境では docker/mysql/init.sql が照合順序を utf8mb4_ja_0900_as_cs（日本語の並び順・大文字小文字を区別）にそろえています。CI でも同じにするため、MySQL が起動したあとに ALTER DATABASE を流しています。照合順序が違うと、日本語の並び順や検索の結果が開発環境と変わりうるためです。

③ 準備

- uses: actions/checkout@3d3c42e…  # v7.0.1  ← コードを取ってくる
- uses: shivammathur/setup-php@eb7c497…  # 2.40.0
  with:
    php-version: '8.3'                  # Dockerfile と同じ 8.3 系
    extensions: pdo_mysql, mbstring, exif, pcntl, bcmath, gd, zip  # Dockerfile と同じ
- uses: actions/cache@55cc834…  # v6.1.0  ← composer のダウンロードを使い回す
- run: composer install --no-interaction --prefer-dist --no-progress
- run: cp .env.example .env && php artisan key:generate   # 使い捨ての APP_KEY

④ 3つのチェック

- name: Pint（書式）
  if: ${{ !cancelled() && steps.install.outcome == 'success' }}
  run: ./vendor/bin/pint --test
- name: PHPStan（静的解析）
  if: ${{ !cancelled() && steps.install.outcome == 'success' }}
  run: ./vendor/bin/phpstan analyse --memory-limit=512M --no-progress
- name: PHPUnit（自動テスト）
  if: ${{ !cancelled() && steps.install.outcome == 'success' }}
  run: php artisan test

ふつうは1つのステップが失敗すると、そこで止まります。ここでは if: を付けて、Pint が ❌ でも PHPStan と PHPUnit は最後まで実行するようにしています。1回の実行で、どこがだめかをまとめて知るためです（準備の composer install が失敗したときは、意味がないので実行しません）。

9このアプリでの作り方のポイント

ひとことで：手元とそろえる、秘密を持ち込まない、部品を固定する、速くする。

① 手元・本番とそろえる

  • PHP は 8.3 系、拡張機能は docker/php/Dockerfile と同じものを入れる。
  • MySQL は 8.4、照合順序は utf8mb4_ja_0900_as_cs。
  • チェックのコマンドは quality-check と同じ。手元で緑なら CI でも緑、という状態を保つ。
補足：setup-php は「8.3 系の最新」を入れるので、Dockerfile の 8.3.36 とは細かい版がずれることがあります。実際の版は「PHP の版を表示する」ステップで毎回ログに出しています。完全に同じにしたいなら Docker で回す方法もありますが、毎回イメージを作るぶん遅くなるので、速さを優先しました。本番と同じイメージでの確認は E2E（手元）が受け持ちます。

② 秘密情報を持ち込まない・権限を絞る

  • 本番の .env.production・AWS の鍵は一切使わない。APP_KEY はその場で作って捨てる。
  • DB のパスワードは CI 専用の使い捨ての値なので、ファイルに書いても問題ない。
  • ワークフローの権限は 読み取りだけ（contents: read）。persist-credentials: false で、取ってきたコードに GitHub の認証情報を残さない。

③ 外部の部品は「コミットの値」で固定する

actions/checkout@v7 のように書くと、作者が v7 の指す中身を差し替えたとき、知らないうちに別のコードが動きます。実際に、有名なアクションが乗っ取られて中身を書き換えられた事件もありました。そこで @3d3c42e… のようにコミットの値（SHA）で固定し、横に # v7.0.1 と人が読める版を書いています。上げるときは両方を書き換えます。

④ 速くする

  • キャッシュ：composer のダウンロードを使い回す。composer.lock が変わったときだけ作り直す。
  • 古い実行を止める：同じ PR に続けて push したら、前の実行はやめる。
  • ジョブは1つ：3つのチェックで準備（PHP・composer）を共有する。

⑤ ドキュメントだけの PR でも回す

「docs だけの変更なら CI を飛ばす」設定（paths-ignore）もできます。ただし「CI が ✅ でないとマージできない」設定（10章）と組み合わせると、CI が始まらないままマージできなくなる落とし穴があります。数分で終わり無料なので、毎回回すことにしました。

⑥ 入れなかったもの

もの入れない理由
E2E テスト（Playwright）本番イメージのビルドとブラウザの準備で1回 5〜10分かかる。画面まわりを変えたときに手元で回す運用で足りている。必要になったら「手動で動かせる別のワークフロー」として足す
負荷試験（k6）CI のランナーは他と CPU を分け合うので数字がぶれ、比べられない
フロントのビルド（vite）@vite を使うのは使っていない welcome.blade.php だけで、テストに影響しない
CD（自動デプロイ）3章のとおり

10導入の流れ

ひとことで：ci.yml を置いた PR そのもので CI を試し、わざと ❌ も出して確かめる。

  1. Issue とブランチ：Issue #128 → chore/128-github-actions-ci
  2. ci.yml を書く：.github/workflows/ci.yml
  3. PR を作る：ci.yml を含む PR そのものに CI が動く（PR のブランチにある ci.yml が使われるため）。✅ になるのを確かめる
  4. わざと失敗させる：書式を崩したコミットを1回 push して ❌ になることを確かめ、すぐ元に戻す。「失敗をちゃんと失敗と言えるか」の確認
  5. ドキュメント：README（CI の表示と説明）、開発ルール（PR で CI が ✅ であること）、設計書（CD を作らない理由と将来案）
  6. マージ（人が行う）→ main でももう一度 CI が動く
  7. ブランチ保護を設定する（人が GitHub の画面で行う）

ブランチ保護（マージ前の必須チェック）

CI を作っただけでは、❌ のままでもマージボタンは押せます。GitHub の設定で 「CI が ✅ でないと main にマージできない」を有効にして、初めて抜けがなくなります。

リポジトリの Settings → Rules → Rulesets → New branch ruleset
  対象ブランチ：main（Include default branch）
  ☑ Require status checks to pass
      追加するチェック：品質チェック（Pint・PHPStan・PHPUnit）
  ☑ Block force pushes

チェックの名前は、一度 CI が動いたあとでないと候補に出てきません。そのため、CI のマージ後に設定します。

11❌ が出たときの見方・直し方

ひとことで：ログで「どのステップの何行目か」を見て、手元で同じコマンドを回して直す。

  1. PR 画面の下にある「Some checks were not successful」の Details を押す（または PR の Checks タブ）
  2. ❌ が付いたステップを開くと、そのときの出力（ログ）が読める
  3. 手元で同じコマンドを回して再現する 
    docker compose exec -T php ./vendor/bin/pint --test
docker compose exec -T php ./vendor/bin/phpstan analyse --memory-limit=512M
docker compose exec -T php php artisan test
  4. 直してコミット・push すると、CI が自動でもう一度動く
状況考えられる原因
手元は ✅ なのに CI だけ ❌ファイルのコミット忘れ（git status を見る）、手元の DB や .env に頼っている、PHP の細かい版の違い
準備（composer install）で ❌composer.json と composer.lock がずれている。パッケージの配布元が一時的に落ちている
コードと関係なく ❌GitHub 側の一時的な不調。Actions の画面の Re-run jobs でやり直す

12用語ミニ辞典

CD
継続的デリバリー／デプロイ。チェック済みの変更を本番まで自動で届ける仕組み。このアプリでは作らない
GitHub Actions
GitHub に組み込まれた自動実行の仕組み。公開リポジトリは無料
ワークフロー
.github/workflows/ に置く YAML ファイル。自動実行の手順書
ランナー
ワークフローを実行する使い捨てのコンピューター
ジョブ／ステップ
ジョブはランナー1台ぶんの作業のまとまり。ステップはその中の1つ1つの作業
アクション
公開されている作業の部品。uses: で呼び出す
サービスコンテナ
ジョブの横で一緒に動かすコンテナ。テスト用 DB など
SHA（コミットの値）
コミットごとに付く40桁の識別子。中身が変わると値も変わるので、版の固定に使える

main へのマージに条件（CI が ✅ など）を付ける GitHub の設定
ステータスチェック
