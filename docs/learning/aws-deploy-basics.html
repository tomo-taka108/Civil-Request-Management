AWS Deploy · 仕組み解説

ブラウザ → ALB → EC2 → RDS を分解する

利用者が URL を打ってから画面が返るまで。その一連の流れの中で、Route53・ACM・リスナー・ターゲットグループ・セキュリティグループ等が「どこで・何のために」登場するのかを順番に追います。値は famigo 相乗り環境の実設定に沿っています。

1リクエストの旅（時系列）

1本のリクエストが左から右へ進み、また戻ってくるまで。各ステップの色付きタグ＝そこで登場する技術。

1

名前解決：ドメイン → IPアドレス

ブラウザが「このドメインのサーバーはどこ？」を調べる（DNS）。答えを持つのが Route53 ホストゾーン。「このドメイン＝ALB」というレコードを返し、ブラウザは ALB の在り処を知る。まだ通信は始まっていない＝電話帳を引いた段階。

Route53 ホストゾーンDNS
2

ブラウザが ALB に接続（HTTPS・443）

得た IP（＝ALB）へ接続。https:// なので 443番ポート・暗号化通信。「このサーバーは本物」を示す ACM証明書 が ALB に載っており、ここで暗号化の握手に使われる。ALB は internet-facing なのでインターネットから直接届く。

443 / HTTPSACM証明書ALB（既存流用）
3

ALB が振り分け先を判断（リスナー・ルール・ターゲットグループ）

ALB は自分で処理せず後ろへ転送する。「443 で受けたものをどうするか」が リスナー。その中の ルール が条件で振り分ける。振り分け先の束が ターゲットグループ。あなたが新規追加するのは「ホスト名＝自ドメインなら本システムのターゲットグループへ」というルール1本と、その受け皿のターゲットグループ。

リスナー（既存）ルール（新規）civil-request-tg-8081（新規）
4

ALB → EC2 のコンテナへ（8081）

ターゲットグループが指すのは EC2 上で動く本システムのコンテナ（Nginx + PHP-FPM、8081番で待受）。ALB がそこへ転送する。このとき「ALB からの 8081 だけ通す」と許可するのが EC2 側の セキュリティグループ（ここに 8081 の許可を1行追加する）。

EC2（既存流用）8081セキュリティグループ（EC2側・1行追加）
5

アプリが処理し、必要なら DB へ（RDS・3306）

Laravel が画面を組み立てる。データが要れば RDS（MySQL） に 3306番で問い合わせる。RDS は Private サブネット（インターネットから直接触れない場所）にいて安全。「EC2 からの 3306 だけ通す」を許可するのが RDS 側の セキュリティグループ。

RDS（既存流用）3306Private サブネットセキュリティグループ（RDS側）
6

来た道を逆に返る

RDS → EC2（Laravel が HTML 完成）→ ALB → ブラウザ、と戻り、画面が表示される。以降の操作も 2〜6 を繰り返す。

2用語辞典（役割で理解する）

各技術を「一言でいう役割」→「たとえ話」で。新規/既存の区分つき。

VPC 既存・参照

役割：AWS 上に区切った“自分専用の閉じたネットワーク区画”

この中に EC2 や RDS が置かれる。外との出入口や内部の部屋割りをまとめて管理する土地のようなもの。famigo が作った famigo-vpc（10.0.0.0/16）にそのまま同居する。

たとえ：1棟のオフィスビル。この建物の中に部屋（サブネット）があり、人（サーバー）が働いている。

サブネット / AZ（アベイラビリティゾーン） 既存・参照

役割：VPC をさらに細かく区切った“部屋”。AZ は物理的に離れたデータセンター

Public サブネット＝インターネットと行き来できる部屋（ALB・EC2 を置く）。Private サブネット＝外から直接入れない奥の部屋（RDS を置く）。AZ は「東京リージョン内の、電源も建物も別の複数拠点」。1a と 1c の2か所に分けておくと、片方の拠点が落ちても全滅しない。だからサブネットは 1a 用・1c 用と2つずつ用意されている。

たとえ：ビル内の部屋割り。受付ロビー（Public）は誰でも入れるが、金庫室（Private）は関係者だけ。AZ は「別の街に建てた同じビル」で、災害の同時被災を避ける保険。

Internet Gateway（IGW） 既存・参照

役割：VPC とインターネットをつなぐ唯一の“正面玄関”

これが無いと VPC の中は完全に外界から隔離される。Public サブネットは IGW への通り道を持つのでインターネットと通信できる。今回の環境は NAT ゲートウェイが無い（コスト削減）ため、EC2 は Public に置いて IGW 経由で直接外と通信している。

たとえ：ビルの正面玄関。ここを通らないと外に出られない／外から入れない。

ALB（Application Load Balancer） 既存・参照

役割：外からのリクエストを受け、後ろのサーバーへ振り分ける“受付・案内係”

利用者は常に ALB に接続し、ALB が中身（どの EC2 / どのコンテナ）へ流すかを決める。HTTPS の暗号化解除もここで行う。1台の ALB で複数システム（famigo と本システム）を捌ける＝これが「相乗り」の要。

たとえ：ビルの総合受付。来訪者は受付にだけ話しかければよく、受付が「その用件は8080号室、こちらは8081号室」と案内してくれる。

リスナー / ルール / ターゲットグループ ルール・TGは新規

役割：ALB の“受付マニュアル”。受け口・振り分け条件・行き先の3点セット

リスナー＝「何番ポートで待つか」（443 リスナー＝HTTPS を待つ窓口）。ルール＝「どんな条件のリクエストをどこへ送るか」（例：ホスト名が自ドメインなら…）。ターゲットグループ＝「送り先サーバー群の名簿」。ここに ヘルスチェック 設定があり、名簿内のサーバーが生きているか定期的に /health を叩いて確認する。死んでいれば振り分け対象から外す。

たとえ：受付の対応マニュアル。「443番窓口（リスナー）に来た人のうち、“土木要望の件”と言った人（ルール）は8081号室グループ（ターゲットグループ）へ通す。各号室には毎分“生きてますか”と内線（ヘルスチェック）して、応答が無い部屋には客を通さない」。

ポート番号（443 / 8080 / 8081 / 3306） 8081が新規

役割：1台のサーバーの中の“どの窓口(サービス)宛てか”を示す番号

同じIPアドレスでも、ポート番号でサービスを区別する。443＝HTTPS（外向けの標準）、8080＝famigo コンテナ、8081＝本システムのコンテナ（新規）、3306＝MySQL。ALB は外から 443 で受け、内側では 8081（本システム）へ渡す。

たとえ：ビルの代表電話は1つ（IP）でも、内線番号（ポート）で部署が分かれている。「443番窓口」「8081号室」「3306号室（DB）」。

セキュリティグループ（SG） EC2側に1行追加

役割：サーバー1台ごとに付く“通信の許可リスト（ファイアウォール）”

「誰から・何番ポートへの通信を通すか」を明示的に許可する。既定は全部拒否で、許可した分だけ通る。
・EC2 の SG：「ALB からの 8080 と 8081 を許可」（8081 の行を新規追加する）
・RDS の SG：「EC2 の SG からの 3306 だけ許可」。“IP ではなく相手の SG を指定”できるのがポイントで、これにより「EC2 からの通信だけ DB に通す」を安全に表現できる。

たとえ：各部屋のドアに貼った入室許可名簿。「受付(ALB)から来た8081番の用件のみ入室可」「DBの部屋は“EC2グループの人”以外お断り」。

EC2 既存・参照

役割：実際にアプリを動かす“仮想サーバー（コンピュータ）”

この上で Docker が動き、famigo のコンテナ（8080）と本システムのコンテナ（Nginx+PHP-FPM、8081）が同居する。docker-compose・ネットワーク・Volume を分けて、片方のデプロイがもう片方に影響しないようにする。

たとえ：1台の作業机。その上で2つの業務（famigo と本システム）を、書類の山を分けて並行して進めるイメージ。

RDS スキーマは新規

役割：AWS が管理してくれる“データベース専用サーバー”（MySQL）

データの保存先。バックアップやパッチ適用を AWS が面倒みてくれる。Private サブネットにいて外から直接触れない。相乗りでは、既存の famigo-mysql の中に本システム専用のスキーマ（データベース）と専用ユーザーを新規に作る（最小権限）。インスタンス本体の設定は変えない。

たとえ：1つの大きな書庫（RDS インスタンス）の中に、famigo 用の棚と本システム用の棚（スキーマ）を分けて置く。鍵（ユーザー）も別々で、自分の棚しか開けられない。

Route53 ホストゾーン 新規

役割：ドメイン名と行き先（ALB等）を対応づける“電話帳”（DNS）

「このドメイン＝この ALB」というレコードを持つ。ブラウザは最初にここを引いて ALB の在り処を知る。本システムは独自ドメインを新規取得し、そのホストゾーンを新規作成する。famigo の既存ドメインには影響しない。

たとえ：電話帳。「“○○社”という名前で調べると、この番号（ALB）につながる」と載っている。

ACM 証明書 新規

役割：HTTPS 通信を成立させる“身分証明書”（TLS/SSL 証明書）

「このドメインのサーバーは確かに本物」を証明し、通信を暗号化する。ブラウザの鍵マークの正体。ALB に載せて使う。AWS の ACM で無料発行でき、自ドメイン用に新規発行する（DNS 検証のためホストゾーンが必要）。

たとえ：受付に掲げる公的な認可証。これがあると来訪者は「偽サイトではなく本物だ」と安心して暗号通話できる。

3いちばん短いまとめ

ブラウザは Route53 で ALB の在り処を知り、443/HTTPS で ALB に接続する（ACM証明書で暗号化）。ALB は リスナー＋ルール で「本システム宛て」と判断し、ターゲットグループ 経由で EC2 の 8081 コンテナ へ転送する（SG が通信を許可）。アプリは 3306 で RDS に問い合わせ（SG が EC2 だけ許可、Private サブネットで保護）、結果を組み立てて逆順に返す。

このうち 新規に作るのは：Route53 ホストゾーン、ACM 証明書、ALB のルール＋ターゲットグループ、EC2 の SG に 8081 許可1行、RDS の新規スキーマ＋ユーザー、そして EC2 上の本システムコンテナ。VPC・サブネット・IGW・ALB本体・EC2本体・RDS本体は既存を “参照するだけ”（Terraform では data source）。
