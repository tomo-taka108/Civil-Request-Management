# パフォーマンステスト（負荷試験）設計書

本書は、負荷試験の目的・方法・結果を定義する。実行手順は [perf/README.md](../perf/README.md)、
テスト全体の中での位置づけは [学習用メモ testing-basics.html](learning/testing-basics.html) を参照。

---

## 0. 本書の位置づけと、数値の扱い方

### 0.1 なぜ行うか

[要件定義書](requirements.md) 4.2 に「想定同時利用者数：最大30人」「想定データ量：年間最大1,000件程度」
（4.3 で保存期間3年）とあるが、これまで**応答の速さを一度も測っていなかった**。
EC2 のメモリ・CPU は実測した（[インフラ設計書](infrastructure-design.md) 3.4）が、負荷はかけていない。

### 0.2 測定値を本番の実力の根拠にしないこと

負荷をかける側（k6）・アプリ・DB が **同じ PC の上で CPU を取り合う**。また DB は同じ PC 上の MySQL で、
本番（RDS）との間のネットワークの往復が無い。得られる値は「この PC でこの構成のとき」の値にすぎない。

| 用途 | 可否 |
|---|---|
| 前回との比較（遅くなっていないか） | ○ 主な目的 |
| どこが詰まるかの特定 | ○ |
| 改善の前後比較 | ○ |
| 「本番で1秒以内」と言う根拠 | ✕ 使わない |

### 0.3 本番には負荷をかけない

本番の EC2（t3.micro）は famigo と共用のため、負荷試験は**ローカルでのみ**行う。CI でも実行しない
（共有のサーバーは他の処理と CPU を分け合い、数値が毎回ぶれて比べられないため）。

## 1. ツールと合格の目安

**k6** を使う（JavaScript でシナリオを書く。選定理由は学習用メモ 5章）。シナリオは素の JavaScript
（このプロジェクトは TypeScript を使っていないため）。

| 項目 | 目安 | 理由 |
|---|---|---|
| 普段の画面の応答時間 | **p95 < 1秒**（画面ごと） | 平均は遅い一部の人の体験を隠すため p95 で見る。値は SnsTimeLineApp と同じ |
| CSV 出力（全件） | p95 < 3秒 | 全件を書き出す重い操作で、使う頻度も低い |
| 失敗率 | 1% 未満 | エラーで速く返っていても意味がない |
| チェック成功率 | 99% 超 | 「ログイン画面に戻されていない」等の確認 |

## 2. 試験専用の環境

`docker-compose.perf.yml`（プロジェクト名 `civil-perf`・ポート **8082**）。

| 項目 | 内容 | 理由 |
|---|---|---|
| nginx・php | **本番と同じイメージ**（`Dockerfile.prod`） | 開発用イメージ（ソースをマウント・dev 依存あり）では本番と速さが違う |
| MySQL | 試験専用のコンテナ（DB 名 `civil_request_perf`）。**データはメモリ上**で、止めると消える | 開発用 DB を汚さない。毎回まっさらな同じ状態から測る |
| APP_KEY | 実行のたびに `run-perf.sh` が使い捨ての値を作る | 鍵をリポジトリに置かない |
| 本番との違い | HTTPS でないため Cookie の Secure 属性を外す／写真はローカル保存／ログは CloudWatch に送らない | — |

開発用の環境（`docker-compose.yml`・ポート 8081）とは、プロジェクト名・ネットワーク・DB がすべて別。

## 3. 試験データ

`database/seeders/PerfDataSeeder.php`。

| 項目 | 件数 | 根拠 |
|---|---|---|
| 事務所 | 3 | 体験用サンプルと同じ3事務所 |
| 職員 | 30人（各事務所10人。部署は道路・河川・砂防に分散）＋管理者1人 | 想定同時利用者数30人 |
| 案件 | **3,000件**（各事務所1,000件）。受付日は過去3年に分散 | 年間1,000件 × 保存3年 |
| 対応履歴 | 約7,000件（未対応は0件、対応中は1〜3件、対応完了は1〜4件） | 古い案件ほど対応完了の割合が高い |
| 論理削除済み | 案件の1% | 一覧・集計から除く処理も含めて測る |
| 現場写真 | なし | 保存先のファイルが必要になり、準備が重くなるため |

- **乱数のシードを固定**し、毎回同じデータにする（前回と比べるため）。
- 文面・住所・要望者は体験用サンプル（すべて架空）を使い回す。画面の重さを実際の文章量に近づけるため。
- **試験専用 DB 以外では動かない**（DB 名が `civil_request_perf` でない、または空でないときは止まる）。
- 3,000件は**試験の前にまとめて入れておく**データで、試験中に入力するものではない。

## 4. シナリオ

### 4.1 普段の業務（`perf/scenarios/daily.js`）

30人がそれぞれ次の「業務の一回り」を繰り返す。操作の合間に2〜5秒の間（画面を読む・考える時間）を入れる。

```
最初に1回ログイン
→ ダッシュボード → 一覧 → 条件を変えて検索 → 案件の詳細
→ ときどき（20%）地図を開く（画面 ＋ ピンのデータ）
→ ときどき（10%）自分の部署の案件に対応履歴を1件書く
```

| 段階 | 時間 | 人数 |
|---|---|---|
| 始業 | 30秒 | 0 → 10人 |
| 全員がそろう | 30秒 | 10 → 30人 |
| **全員が使い続ける** | **2分** | **30人** |
| 終わる | 20秒 | 30 → 0人 |

検索条件は、未完了のみ・緊急性「高」・キーワード（土砂／草／護岸）・受付日の期間・30日以上動きなし、から選ぶ。

### 4.2 CSV 出力（`perf/scenarios/export.js`）

使う頻度は低いが1回が最も重い操作のため、普段の業務とは分けて1人ずつ測る。
管理者（全事務所・約3,000件）と一般職員（自事務所・約1,000件）で5回ずつ。

### 5.5 仮説の答え合わせ

試験前に、コードを読んで「詰まりそうな所」を予想していた（学習用メモ 9章）。

| 仮説 | 結果 |
|---|---|
| PHP の同時処理数（php-fpm は既定の5） | **問題なし**。1画面が数十ms で終わるため、60人でも5つの処理枠で回り、順番待ちによる遅れは見られなかった |
| 地図はピンを件数の上限なしで全部返す | **速さは問題なし、データ量に課題**。サーバー側は約0.1〜0.25秒だが、管理者では 1.77MB になる（6.1） |
| ダッシュボードは開くたびに全件を集計 | **問題なし**（下記の統計情報の件を除く） |
| キーワード検索（LIKE の部分一致）は索引が効かない | **問題なし**。3,000件では全件を見ても約25ms |

### 5.6 試験の中で見つけたこと：一括投入の直後は MySQL の統計情報が古い

最初の計測で、ダッシュボードだけ **まれに0.8〜0.95秒**かかった（p99 803ms）。調べると、ダッシュボードの
「30日以上動きなし」の件数を数える SQL が、**データを一括投入した直後だけ**、対応履歴の索引を使わずに全件を
見ていた（約0.58秒・約356万行を確認）。

| | 対応履歴の調べ方 | 時間 |
|---|---|---|
| 投入直後 | 索引を使わず全件 | 0.576秒 |
| `ANALYZE TABLE` で統計情報を更新した後 | 索引を使う | 0.006秒 |

MySQL は「どの順に調べると速いか」を、表ごとの統計情報から決める。大量のデータを一度に入れた直後は統計が
古いままのため、遅い調べ方を選ぶ。統計は自動でも更新されるので、しばらくすると速くなる。

- **本番への影響**：データが少しずつ増える通常運用では起きにくい。体験用サンプルの入れ替え（`sample:refresh`）も
  約75件と少なく、全件を見ても一瞬で終わるため影響しない。将来、既存の台帳など**大量のデータを一括で取り込む**
  ときは、取り込んだ後に `ANALYZE TABLE` を実行する
- **試験での対応**：`PerfDataSeeder` の最後で `ANALYZE TABLE` を実行し、「運用中のふだんの状態」から測る。
  対応後はダッシュボードの p99 が 803ms → 67ms になった

### 5.7 まとめ

想定（30人・3,000件）に対して、**全画面が目安（p95 1秒未満）を大きく下回った**。想定の2倍（60人）でも
失敗は無く、目安内に収まった。速さの面で今すぐ直すべき箇所は無い。

## 6. 今後検討

### 6.1 地図のピンのデータ量

地図のピンのデータ（`/map/pins`）は、条件に合う案件を全件 JSON で返す。サーバー側の処理は速いが、データ量が
一般職員で約0.6MB、管理者で約1.8MB ある。本番では利用者の回線でこれをダウンロードするため、回線が遅いと
数秒かかりうる。nginx で圧縮（gzip）していないことも一因。

対策の候補：

| 案 | 効果 | 注意点 |
|---|---|---|
| nginx で JSON を gzip 圧縮する | 大きく減る見込み（JSON は圧縮が効きやすい） | nginx の gzip は HTML も必ず圧縮する。CSRF トークンを含む HTML の圧縮は、BREACH という攻撃の条件の1つになるため、方式を検討してから入れる |
| ピンのデータの項目を減らす | 中程度（URL などを画面側で組み立てる） | 地図画面の JavaScript の修正が要る |
| 地図の初期表示を「未完了のみ」にする | 件数が大きく減る | 画面の仕様変更（要件・画面設計書の更新が要る） |

### 6.2 管理者の操作を含むシナリオ

k6 のシナリオは一般職員30人のみ。管理者は人数が少ないため手で計測した（5.4）。管理者の利用が増えるなら、
シナリオに加える。

### 6.3 本番の環境での確認

数値はこの PC の値（0.2）。本番は DB が RDS で、EC2（t3.micro）を famigo と共用している。本番の速さは、
CloudWatch のログ（nginx の `duration_s`）で日々の実際の応答時間を見て確かめる（[ログ・監視設計書](logging-and-monitoring.md)）。
